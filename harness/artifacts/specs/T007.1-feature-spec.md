## Title

Blog Sidebar Refinements

---

## Feature Goal

Refine the blog sidebar and shared content layout so archive navigation is more usable, tag discovery is more compact, and long-form content has a less constrained reading width.

---

## User Value

Readers can browse blog content by year and month more efficiently, scan popular tags in a denser format, and read page content in a layout that feels less squashed across the shared site shell.

---

## In Scope

List the behaviours and capabilities included in this feature.

- The Monthly Archive panel groups month links beneath distinct year headings shown in descending year order.
- Each year heading displays the total number of posts published in that year.
- Each year heading links to a year-level archive route at `/blog/archive/[year]`.
- The year-level archive route lists all posts for the selected year using the same archive experience pattern used by existing blog archive views.
- The year-level archive route supports static generation consistent with existing archive routing patterns.
- A valid year-level archive URL with no matching posts presents an explicit empty state.
- The Top Tags panel presents tags as wrapping chip-style elements rather than a vertical list.
- Tag chips preserve existing tag count visibility, destination link behavior, and active-state indication.
- The shared shell or container used by the blog and other pages is widened so the main content column is less narrow.
- The width adjustment applies consistently to pages that use the shared shell, including the main blog index and archive views.

---

## Out of Scope

Explicitly list what this feature does NOT include.

This prevents scope creep.

- Redesigning the overall blog information architecture beyond the specified year grouping, tag presentation, and shared width refinement.
- Changing tag ranking logic, archive sorting rules beyond the specified descending order, or blog post content.
- Adding new filtering dimensions, search, or pagination behavior beyond what is required to support the year-level archive route.
- Introducing a new visual theme or bespoke per-page layout overrides outside the shared shell or container adjustment.

## Acceptance Criteria

Define the conditions that must be satisfied for the feature to be considered complete.

Acceptance criteria should be:

- specific
- observable
- bounded
- testable

Prefer verifiable outcomes over subjective wording.

Stronger examples:

- A shared root layout wraps all pages under the main app route tree.
- Header navigation is visible on all pages using the shared layout.
- The layout uses the standard centered content container defined by the design system.

Avoid vague examples such as:

- The layout feels polished.
- The spacing looks good.
- The page feels consistent.

- In the Monthly Archive panel, archive months are grouped under year headings, with years displayed from most recent to oldest.
- Within each year group, month entries are displayed from most recent to oldest.
- Each year heading displays a four-digit year label and the total number of posts in that year in the heading text.
- Activating a year heading navigates to `/blog/archive/[year]` for that year.
- Visiting `/blog/archive/[year]` for a year that has published posts displays only posts from that year.
- The year-level archive view follows the same page pattern as existing archive listings by presenting a standard archive listing experience rather than a unique one-off layout.
- The year-level archive route is statically generated for available years using the same generation approach as other archive routes.
- Visiting a syntactically valid year archive URL that resolves to no posts shows an explicit empty state message on the page.
- In the Top Tags panel, tags render in a horizontal wrapping arrangement so multiple chips can appear on the same row when space allows.
- Each tag chip continues to show the tag label, post count, link destination, and active-state treatment already established for tag navigation.
- Pages using the shared shell or container present a visibly wider main content column than before this task.
- The widened shared layout is applied consistently on `/blog`, `/blog/archive/[year]`, `/blog/archive/[year]/[month]`, `/blog/tag/[tag]`, and other pages using the same shared shell or container.
- Existing sidebar functionality from T007 remains intact, including archive navigation, tag navigation, and active-state behavior.

## Dependencies

Identify anything required before implementation can proceed.

Examples:

- existing components
- content requirements
- external services

- Existing blog post publication metadata must be available and reliable enough to derive year and month archive groupings.
- Existing blog archive and tag navigation behavior must remain available as the baseline interaction model.
- Shared shell or container usage across relevant pages must be identifiable so the width refinement can be applied centrally.

## Risks

Identify potential issues that could affect implementation.

Examples:

- unclear content requirements
- dependency on future features
- unknown technical constraints

- The shared width change could unintentionally affect non-blog pages that use the same shell or container if success criteria are interpreted too broadly during implementation.
- Archive behavior may diverge across month and year views if the year-level route is implemented as a separate pattern instead of matching existing archive behavior.
- Empty-state handling for valid but contentless year routes may be ambiguous if routing and data-loading logic do not clearly distinguish empty results from invalid routes.
