## Title

Editorial UI System Refactor from Design Reference

---

## Feature Goal

Refactor the production site UI so that all pages conform to the editorial design system defined in `harness/design-system/design-system.md`. The refactor introduces a reusable editorial component layer, aligns layout and typography across all routes, and improves the visual presentation of every page — while preserving all existing routing, data logic, API behaviour, and tests.

The `/tmp-design-reference` directory serves as read-only visual and structural reference material. No files or code may be copied from it. Design patterns must be extracted, interpreted, and re-implemented as production-ready components.

---

## User Value

Visitors experience a cohesive, calm, and readable site that feels intentionally designed rather than assembled from defaults. Consistent typography, spacing, and layout reinforce professionalism and make content easy to consume across all pages and devices.

---

## In Scope

- **Global layout alignment**: The root layout and shared shell reflect the editorial design system — centered content container (`max-w-3xl` to `max-w-4xl`), consistent vertical spacing, and typography driven by the Inter font family.
- **New header component**: A reusable header with simple desktop navigation links and a working collapsible mobile menu. Navigation items cover existing routes (Home, Blog, About, Contact).
- **Simplified footer component**: A lightweight, editorial-tone footer replacing any existing footer. Minimal content — no complex link grids or social icons.
- **Reusable editorial component layer**: A small set of shared components that downstream pages compose from:
  - Site header (with responsive nav)
  - Site footer
  - Section wrapper (consistent section spacing and padding)
  - Hero section (page-level introductory block)
  - Content block (standard prose container)
- **Homepage redesign**: The homepage is restructured into clearly defined editorial sections (hero, content sections) using real content rather than placeholder text.
- **Blog page presentation improvement**: The blog listing page and individual blog post pages retain all existing data-fetching logic, routing, and API behaviour but adopt improved editorial typography, spacing, and card/list presentation.
- **Contact page simplification**: The contact page is simplified to a clean editorial layout. Any fake or demo form submission behaviour is removed. A static contact form or informational layout is acceptable.
- **Consistent spacing and typography**: All pages use the spacing scale and typographic hierarchy defined in the design system. No arbitrary spacing values or inconsistent font sizing.
- **Colour system compliance**: UI uses the neutral-dominant palette with dark red (`#7A1C1C`) used sparingly for accents. No colour-heavy decoration.
- **Responsive design**: All pages and components render cleanly on mobile, tablet, and desktop breakpoints. Mobile-first approach.
- **Accessibility baseline**: Sufficient colour contrast, logical heading order, readable font sizes, visible focus states, and meaningful link text across all pages.

---

## Out of Scope

- Changes to routing structure, URL patterns, or page tree
- Changes to blog data-fetching logic, markdown parsing, or API routes
- Changes to test files or test infrastructure
- Introduction of new pages or routes
- Addition of large UI component libraries or unnecessary npm dependencies
- Dark mode or theme switching
- Animation or motion design beyond minimal hover/focus transitions
- CMS integration or dynamic content management
- SEO metadata changes (unless directly required by layout restructuring)
- Copying any files or code from `/tmp-design-reference` into production
- Performance optimisation work beyond what naturally results from simplification

---

## Acceptance Criteria

1. The global root layout uses a centered content container with a maximum width between `max-w-3xl` and `max-w-4xl`.
2. A shared site header is rendered on every page, containing navigation links to Home, Blog, About, and Contact.
3. The site header displays horizontal navigation on desktop viewports and a collapsible menu on mobile viewports.
4. The collapsible mobile menu opens and closes when activated and displays the same navigation links as the desktop header.
5. A shared site footer is rendered on every page with minimal, editorial-appropriate content.
6. Reusable editorial components exist for: site header, site footer, section wrapper, hero section, and content block.
7. The homepage contains at least one hero section and one or more structured content sections with real (non-placeholder) content.
8. The blog listing page displays blog posts using the existing data-fetching logic with updated editorial presentation (typography, spacing, and layout).
9. Individual blog post pages retain their existing routing and data logic and render content with editorial typography and spacing.
10. The contact page renders a simplified layout without any fake or demo form submission behaviour.
11. Typography across all pages uses the Inter font family with heading sizes following the design system hierarchy (H1: 36–48px, H2: 30–36px, H3: 24–28px, body: 16–18px).
12. Spacing between sections follows the design system scale and uses consistent vertical rhythm (`space-y-10` to `space-y-16` for sections, `space-y-4` to `space-y-6` for content groupings).
13. The colour palette is neutral-dominant with dark red (`#7A1C1C`) used sparingly for accents and active states.
14. All existing routes continue to resolve correctly and return the expected content.
15. All existing tests (unit, integration, end-to-end) pass without modification.
16. The blog API route (`/api/blog`) continues to function identically.
17. No files or components are copied directly from `/tmp-design-reference`.
18. No unnecessary third-party dependencies or large UI libraries are added to the project.
19. The UI presents a cohesive and consistent visual appearance across Home, Blog, About, and Contact pages.
20. All pages render correctly on mobile, tablet, and desktop viewports.

## Dependencies

- The editorial design system document (`harness/design-system/design-system.md`) is the authoritative visual reference and must be followed for all colour, typography, spacing, and layout decisions.
- The `/tmp-design-reference` directory must be available as read-only structural and visual reference during the Design and Build stages. It will be removed after task completion.
- Existing production components (`site-nav.tsx`, `site-shell.tsx`, page files) provide the current structure that will be refactored.
- The Inter font must be available (either via Google Fonts or a local/bundled approach compatible with Next.js).

---

## Risks

- **Subjectivity of "editorial" tone**: The design system provides clear guidelines, but translating them into specific Tailwind classes and component structures requires design interpretation. The Design stage must resolve any ambiguity.
- **Mobile menu complexity**: Implementing a working collapsible mobile menu without introducing a large UI library requires careful implementation. The approach should remain lightweight (CSS-driven or minimal JS state).
- **Regression in existing functionality**: Refactoring layout components that wrap all pages carries risk of breaking existing page rendering or data flow. All existing tests must pass after the refactor.
- **Scope creep during implementation**: The breadth of the refactor (all pages, new component layer, homepage redesign) could lead to scope expansion. Implementation must stay within the defined acceptance criteria.
