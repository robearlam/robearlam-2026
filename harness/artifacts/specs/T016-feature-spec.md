## Title

Dependabot Vulnerability Remediation

---

## Feature Goal

Bring the dependency tree of the site (`src/package.json` and `src/pnpm-lock.yaml`) to patched versions for every open Dependabot alert in the reference set, in one coordinated update, with no change to site behaviour or appearance.

The reference set is the 126 open Dependabot alerts as of 2026-10-19 (7 critical, 40 high, 64 medium, 15 low). It can be re-fetched with `gh api repos/robearlam/robearlam-2026/dependabot/alerts --paginate`. Alerts raised after 2026-10-19 are not part of the reference set (see Out of Scope).

---

## User Value

The site owner stops shipping known critical vulnerabilities (notably remote code execution, SSRF and cache poisoning in `next` 16.2.6) and clears the alert backlog. Visitors notice nothing: every route renders and behaves as it does today.

---

## In Scope

- Upgrading `next` (and `eslint-config-next` if present, to match) from 16.2.6 to 16.3.8 or later.
- Upgrading other direct dependencies and devDependencies where a newer version pulls in a patched transitive package. Known fix targets: `mermaid` >= 11.16.1, `vite` >= 8.0.16, `vitest` >= 4.1.11, `sharp` >= 0.35.4.
- Resolving transitive alerts for: `hono`, `@hono/node-server`, `undici`, `dompurify`, `mermaid`, `js-yaml`, `ip-address`, `fast-uri`, `brace-expansion`, `vite`, `vitest`, `@vitest/mocker`, `sharp`, `postcss`, `postcss-selector-parser`, `nanoid`, `browserslist`, `baseline-browser-mapping`, `source-map-js`, `proxy-addr`, `qs`, `@babel/core`, `@modelcontextprotocol/sdk`. Order of preference: direct bump first, `pnpm.overrides` only where the upstream parent has not adopted the fix.
- Regenerating `src/pnpm-lock.yaml` consistently with `src/package.json`.
- Minimal code changes in `src/` only where an upgrade forces them (breaking API, deprecation that fails lint or typecheck, or a behavioural regression).
- Recording, in the implementation plan and QA review, a disposition for every alert that stays open: the advisory ID, why no fix is applied (no patched version published, or other), and whether the vulnerable code path is reachable in this site. Known no-patch advisories: `sprintf-js` GHSA-hp3w-g68c-fv3c and one `dompurify` advisory.
- Running the validation suite against the upgraded tree, or recording what could not be run (see Verification Evidence).

---

## Out of Scope

- Major-version upgrades not required to clear an alert (for example React or Tailwind majors).
- Adding new dependencies or replacing a library with another.
- CI security scanning, or Dependabot/Renovate configuration (B015).
- Changing Dependabot alert states in GitHub. Dismissals are done by the human using the dispositions this task records.
- Any visual, content or feature change to the site.
- Alerts raised after 2026-10-19. They are follow-ups, unless one is cleared at no extra cost by a bump already being made, in which case it may be noted but is not required.
- The untracked root `package-lock.json` and `src/package-lock.json` (decision below).

### Decision on stray npm lockfiles

Out of scope: the task does not delete, ignore, edit, or commit them.

Reasoning:
- They are untracked, so they are not part of the repository's dependency state and Dependabot does not report against them. Dependabot alerts target `src/package.json` and `src/pnpm-lock.yaml`, which is the set this task fixes.
- Deleting or `.gitignore`-ing local files is hygiene, not remediation, and would widen a security change with an unrelated repo-policy decision.
- Constraints that follow: they must not be staged or committed as part of T016; they must not be used as evidence of resolved versions (only `src/pnpm-lock.yaml` counts); and they are noted as a follow-up for the human (delete locally or add to `.gitignore`).

## Acceptance Criteria

Dependency resolution (checked from `src/pnpm-lock.yaml` and `src/package.json`):

1. `src/pnpm-lock.yaml` resolves `next` to 16.3.8 or later, and no other version of `next` is resolved.
2. For each package in the In Scope list, no resolved version in `src/pnpm-lock.yaml` falls inside a vulnerable range of any advisory in the 2026-10-19 reference set, except advisories with a recorded disposition under criterion 4.
3. `src/package.json` and `src/pnpm-lock.yaml` are consistent: the lockfile's importer specifiers match the manifest, and a frozen-lockfile install (`pnpm --dir src install --frozen-lockfile`) would not need to modify the lockfile.
4. Every advisory in the reference set that remains unresolved has a written disposition naming the advisory ID, the package and resolved version, the reason (no patch published, or other), and reachability in this site (reachable, not reachable, or unknown with justification). The two known no-patch advisories (`sprintf-js` GHSA-hp3w-g68c-fv3c and the one `dompurify` advisory) are included.
5. Every `pnpm.overrides` entry added to `src/package.json` is listed in the implementation plan or QA review with the advisory it addresses and the upstream parent it works around. Overrides that do not address a reference-set advisory are not added.
6. No new direct dependency is added, and no direct dependency changes major version unless that change is the only way to clear a reference-set alert (in which case the reason is recorded).

Behaviour (application-owned logic; content in `src/data/` is unchanged):

7. No file under `src/data/` is modified by this task.
8. Application code changes in `src/` are limited to those required by an upgrade, and each is listed with its reason in the implementation plan.
9. `rehype-sanitize` remains in the markdown rendering pipeline.
10. Blog posts that contain Mermaid diagrams still render the diagrams, and sanitised markdown still renders, as covered by existing tests (unit, integration, e2e). Any existing test change is limited to accommodating upgrade-driven output differences and is justified in the plan.
11. The OG image, RSS, sitemap and robots routes (T011/T012) still respond successfully under the production build, covered by existing e2e tests or a recorded manual check.

Verification Evidence:

12. For each of `pnpm --dir src lint`, `typecheck`, `test`, `build` and `test:e2e`, the QA review records one of: passed (with command output evidence), failed, or unverified (with the reason). A command that was not run is never reported as passed.
13. pnpm was not found in the local environment at session start. If it remains unavailable, the local commands in criterion 12 are recorded as unverified, and acceptance is evidenced instead by:
    a. lockfile resolution checks (criteria 1 to 3), done by inspecting `src/pnpm-lock.yaml` and `src/package.json` directly, with each in-scope package's resolved version listed against the fix target; and
    b. a green run of the CI workflow `.github/workflows/playwright.yml` (production build plus Playwright e2e) on the branch or its pull request, cited by run reference, and/or a re-fetch of the alert list showing the post-merge state.
    Without either 13b or local command output, the task may be reported as "resolution verified, runtime validation unverified", and the approver is told this explicitly. Approval is then a human decision.
14. QA compares the alert set at QA time (`gh api repos/robearlam/robearlam-2026/dependabot/alerts --paginate`, if available) with the reference set and reports: alerts cleared, alerts remaining with dispositions, and any new alerts (follow-ups only).

## Risks

- Next.js 16.2 to 16.3 may change caching, metadata image routes, `next/og` or image optimisation behaviour.
- Overrides can force a transitive package beyond what its parent supports, breaking at runtime without failing the build.
- Mermaid and DOMPurify upgrades may change rendered SVG or sanitisation output and break diagrams or tests.
- Runtime validation may be impossible locally (pnpm missing), leaving CI as the only runtime evidence.
- Moving target: new alerts may land before approval; handled by the fixed reference set.
- A no-patch advisory may still be reachable, leaving residual risk the human must accept or dismiss.
