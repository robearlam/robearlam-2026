## Title

Contact Page v1 (Static)

---

## Feature Goal

Provide a dedicated contact page that presents clear contact information and external profile links within the shared global site shell.

---

## User Value

Visitors can quickly find ways to contact the site owner and discover relevant external profiles from a single, easy-to-scan page on desktop and mobile.

---

## In Scope

List the behaviours and capabilities included in this feature.

- A contact page route exists under the application route tree and renders within the shared global shell from T001.
- The page includes a clear page title and short introduction text describing the purpose of the page.
- The page displays one or more static contact methods (for example, email address or contact channel text).
- The page displays external profile links for BlueSky, Mastodon, GitHub, LinkedIn, YouTube, and Dev.to.
- Each required external profile link is represented with a recognizable icon and link label or accessible name.
- All external profile links point to the exact URLs defined in the task.
- The layout is responsive and readable across mobile and desktop viewports.
- The page uses existing site styling patterns and components to remain aligned with the design system.

---

## Out of Scope

Explicitly list what this feature does NOT include.

This prevents scope creep.

- Contact form UI controls for user submission.
- Backend or API integration for message handling.
- Form submission workflows, success/error states, or data persistence.
- Client-side or server-side validation logic.
- CAPTCHA, spam prevention, or abuse mitigation mechanisms.
- Analytics or event tracking instrumentation.
- Advanced interactive profile cards or rich animations beyond basic page presentation.

---

## Acceptance Criteria

Define the conditions that must be satisfied for the feature to be considered complete.

Acceptance criteria should be:

- specific
- observable
- bounded
- testable

Prefer verifiable outcomes over subjective wording.

1. A contact page is reachable at the contact route in the app and is wrapped by the shared global shell used by other site pages.
2. The page renders a visible heading that identifies the page as contact-oriented and includes short introductory copy.
3. The page renders at least one static contact method as plain content with no form input fields or submit actions.
4. The page includes exactly these external profile destinations:
   - BlueSky: https://bsky.app/profile/robearlam.com
   - Mastodon: https://mastodon.social/@RobEarlam
   - GitHub: https://github.com/robearlam
   - LinkedIn: https://www.linkedin.com/in/rob-earlam/
   - YouTube: https://www.youtube.com/playlist?list=PLmTNwpFzRErCW5ibZAkSO8HFSW0Rkiplj
   - Dev.to: https://dev.to/robearlam
5. Each required external profile is presented as an interactive link with a recognizable icon and an accessible name that identifies the destination.
6. External profile links open in a new browser tab and include standard security attributes for external navigation.
7. No contact form behavior exists: no submit button, no submission handler, no validation messages, and no API request for contact submission.
8. On common mobile and desktop viewport widths, content remains readable without horizontal scrolling and link targets remain usable.
9. The page uses existing design-system-aligned typography, spacing, and container conventions already established for the site.

## Risks

Identify potential issues that could affect implementation.

- The task does not prescribe exact contact-method copy, which could cause inconsistent content decisions if not confirmed.
- Icon choice may vary by library or asset availability, potentially affecting visual consistency or recognizability.
- External URL typos could silently break destinations unless explicitly verified.
- If external-link behavior (same tab vs new tab) is not enforced consistently, user experience may be inconsistent.
