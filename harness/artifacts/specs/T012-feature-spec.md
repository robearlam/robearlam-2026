## Title

Auxiliary Site Protocols — RSS Feed, WebFinger, Robots & Sitemap Validation

---

## Feature Goal

Implement the remaining site-level auxiliary protocols needed for subscriptions, discovery, and crawler interoperability: an RSS feed at `/rss`, a WebFinger endpoint at `/.well-known/webfinger`, and validation that the existing `robots.txt` and `sitemap.xml` implementations remain correct.

---

## User Value

- **RSS feed** allows visitors and aggregators to subscribe to blog content via standard feed readers, increasing reach and discoverability.
- **WebFinger** preserves the established Mastodon/ActivityPub identity discovery already published on the live `robearlam.com` domain, ensuring the site continues to act as a stable discovery endpoint for the `acct:RobEarlam@mastodon.social` identity.
- **Robots & sitemap validation** ensures search engines and AI crawlers continue to have correct, uninterrupted access to public content.

---

## In Scope

- RSS 2.0 feed route at `/rss` returning valid XML with correct content type
- WebFinger JSON route at `/.well-known/webfinger` returning the established identity payload
- Review and validation of the existing `robots.txt` implementation in `src/app/robots.ts`
- Review and validation of the existing `sitemap.xml` implementation in `src/app/sitemap.ts`
- Focused tests for new endpoints covering response shape, content type, and data correctness

---

## Out of Scope

- Atom feed or JSON Feed alternatives (only RSS 2.0 is required)
- ActivityPub server implementation or inbox/outbox endpoints
- Dynamic WebFinger lookup for arbitrary accounts (only the single established identity is served)
- Modifications to robots.txt crawler rules unless a defect is discovered during validation
- Modifications to sitemap route inclusion unless a defect is discovered during validation
- Adding `/rss` or `/.well-known/webfinger` to the XML sitemap (service endpoints, not content pages)
- UI changes (no visible feed link or WebFinger badge in the site chrome)

## Acceptance Criteria

### RSS Feed

**AC-1:** A Next.js route handler exists at `src/app/rss/route.ts` that serves the RSS feed at the `/rss` URL path.

**AC-2:** The response returns HTTP `Content-Type: application/rss+xml; charset=utf-8`.

**AC-3:** The RSS channel metadata includes:
- `<title>` sourced from `SITE_NAME` (`"Rob Earlam"`)
- `<link>` sourced from `SITE_URL` (`"https://robearlam.com"`)
- `<description>` sourced from `SITE_DESCRIPTION`
- `<language>en</language>`

**AC-4:** Feed items are generated from `getAllBlogPosts()` in `src/lib/blog/posts.ts`, returned in reverse-chronological order (newest first, matching the existing sort).

**AC-5:** Each feed item includes at minimum:
- `<title>` — the blog post title
- `<link>` — the canonical URL for the post, built using `canonicalUrl()` or `SITE_URL` + `/blog/${slug}`
- `<description>` — the post summary/excerpt
- `<pubDate>` — the publication date in RFC 822 format
- `<guid isPermaLink="true">` — the canonical post URL

**AC-6:** The feed XML is well-formed and validates as RSS 2.0 structure: `<rss version="2.0">` root element containing a single `<channel>` with the above metadata and items.

**AC-7:** Feed URLs use the canonical `SITE_URL` constant already used across the rest of the application; no hardcoded domain strings are introduced.

### WebFinger

**AC-8:** A Next.js route handler exists at `src/app/.well-known/webfinger/route.ts` that serves the WebFinger endpoint at `/.well-known/webfinger`.

**AC-9:** The response returns HTTP `Content-Type: application/jrd+json; charset=utf-8`.

**AC-10:** The response body is a JSON document containing:
- `subject`: `"acct:RobEarlam@mastodon.social"`
- `aliases`: `["https://mastodon.social/@RobEarlam", "https://mastodon.social/users/RobEarlam"]`
- `links` array containing:
  - `{ "rel": "http://webfinger.net/rel/profile-page", "type": "text/html", "href": "https://mastodon.social/@RobEarlam" }`
  - `{ "rel": "self", "type": "application/activity+json", "href": "https://mastodon.social/users/RobEarlam" }`
  - `{ "rel": "http://ostatus.org/schema/1.0/subscribe", "template": "https://mastodon.social/authorize_interaction?uri={uri}" }`

**AC-11:** The endpoint returns the same payload for both:
- The plain path `/.well-known/webfinger`
- The standard query variant `/.well-known/webfinger?resource=acct:rob@robearlam.com`

This preserves functional compatibility with the currently live site behavior.

**AC-12:** The implementation uses Next.js app routing conventions (route handler in the app directory) and does not depend on redirect hacks or middleware rewrites.

### Robots.txt Validation

**AC-13:** The existing `src/app/robots.ts` implementation is reviewed and confirmed to:
- Allow all user agents with `allow: "/"`
- Advertise the sitemap at `${SITE_URL}/sitemap.xml`
- Not block any public content from search or AI crawlers

**AC-14:** No changes are made to `robots.ts` unless a specific defect is discovered. If changes are made, they must be documented in the design note with explicit justification.

### Sitemap Validation

**AC-15:** The existing `src/app/sitemap.ts` implementation is reviewed and confirmed to:
- Include all current indexable routes: home, `/blog`, `/videos`, `/speaking`, `/contact`, and all individual blog post detail pages
- Exclude routes already marked `noindex` (blog archive pages, tag pages)
- Not include service endpoints (`/rss`, `/.well-known/webfinger`)

**AC-16:** No changes are made to `sitemap.ts` unless a specific defect is discovered. If changes are made, they must be documented in the design note with explicit justification.

### Technical Quality

**AC-17:** New endpoints reuse the existing SEO constants (`SITE_URL`, `SITE_NAME`, `SITE_DESCRIPTION`) and the `canonicalUrl()` helper from `src/lib/seo/` where practical. No duplicate source of truth is introduced for site identity, canonical domain, or blog post metadata.

**AC-18:** New protocol endpoints are covered by focused tests verifying response shape, content type, and data correctness.

**AC-19:** All changes pass lint, typecheck, and relevant test suites without regressing existing SEO behavior.

## Risks

- **`.well-known` dot-prefix routing**: Next.js app router may have edge cases with dot-prefixed directory names. The design stage should verify that `src/app/.well-known/webfinger/route.ts` is correctly routed and not ignored by the build tooling.
- **RSS XML generation**: No existing XML generation infrastructure exists in the project. The design stage should select an approach (template literals vs. library) and justify the choice.
- **Content-Type fidelity**: The `application/jrd+json` and `application/rss+xml` content types must be verified in tests to ensure they are not overridden by framework defaults.
