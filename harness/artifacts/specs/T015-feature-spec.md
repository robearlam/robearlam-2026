## Title

Dark Mode Support

---

## Feature Goal

Add site-wide dark mode support. The site respects the user's OS colour scheme preference (`prefers-color-scheme`) by default. A toggle in the header allows users to override this, and their preference is persisted to `localStorage` so it is restored on return visits without a flash of the wrong theme.

The dark mode colour palette is derived from the existing design system. All pages and components are styled consistently in both modes.

---

## User Value

Users who prefer dark mode — for visual comfort, accessibility, low-light environments, or personal preference — currently have no way to use this site without the full white background and light colour scheme. This feature:

- respects the user's OS-level colour preference automatically on first visit
- allows any user to override their preference via a clearly accessible toggle
- persists that preference so repeat visitors are not required to re-toggle
- ensures the experience is consistent and polished across all pages and components

---

## In Scope

- A theme toggle button placed in the site header, visible and usable on all breakpoints (desktop and mobile)
- Dark mode colour palette defined and applied, derived from the existing design system neutral palette
- Tailwind CSS `darkMode: 'class'` strategy for all dark mode styling
- The theme class (`dark`) applied to the `<html>` element
- System colour scheme detection via `prefers-color-scheme` media query as the default for first-time visitors
- `localStorage` persistence of the user's manual toggle choice under a named key
- Synchronous theme application before page paint to prevent Flash of Unstyled Content (FOUC)
- Full site-wide dark mode coverage — all existing pages and components styled for both modes
- Brand and accent colours adjusted in dark mode where necessary to maintain WCAG AA contrast
- Code blocks, tags, metadata, and other secondary UI elements styled appropriately in dark mode
- Design system document (`harness/design-system/design-system.md`) updated with the dark mode colour palette
- Unit and integration tests for theme toggle logic, preference persistence, and FOUC prevention

---

## Out of Scope

- Per-page or per-section theme overrides (dark mode applies globally or not at all)
- Auto-switching theme based on time of day or other signals
- Inverting or theme-adapting images, videos, or external embedded content
- Any modification to the existing light mode colour palette
- A "system" option as a third explicit toggle state (system preference is the default when no `localStorage` value exists; the toggle switches between light and dark only)
- Dark mode for any admin, CMS, or non-public-facing interface

---

## Acceptance Criteria

### AC-1: Toggle Presence and Placement

- AC-1.1: A theme toggle button is present in the site header on all pages
- AC-1.2: The toggle is visible and usable at mobile, tablet, and desktop breakpoints
- AC-1.3: The toggle does not disrupt the existing header layout or navigation at any breakpoint
- AC-1.4: On mobile, the toggle is accessible within the mobile nav layout (does not overflow or overlap other elements)
- AC-1.5: The toggle has a minimum tap/click target of 44×44px

### AC-2: Toggle Affordance and Accessibility

- AC-2.1: The toggle displays a recognisable visual indicator of the current mode (e.g. sun icon for light mode, moon icon for dark mode)
- AC-2.2: The visual indicator changes when the mode is switched
- AC-2.3: The toggle has a descriptive `aria-label` that reflects the action it will perform (e.g. "Switch to dark mode" when currently in light mode)
- AC-2.4: The toggle is keyboard accessible and activatable via the `Enter` or `Space` key
- AC-2.5: The toggle has a visible focus state in both light and dark modes

### AC-3: Theme Behaviour

- AC-3.1: On first visit with no stored preference, the site applies the user's OS `prefers-color-scheme` setting (light or dark)
- AC-3.2: Activating the toggle switches the active theme immediately without a page reload
- AC-3.3: The user's toggle choice is saved to `localStorage` under a stable, named key (e.g. `theme`)
- AC-3.4: On return visits, the stored preference is read and applied before the page paints — no flash of the wrong theme is visible
- AC-3.5: If no value is stored in `localStorage`, the site falls back to the OS system preference
- AC-3.6: The `dark` class is applied to the `<html>` element when dark mode is active

### AC-4: Visual Design — Dark Mode Palette

- AC-4.1: Dark mode uses a deep neutral background that is not pure black (e.g. a dark grey tone derived from the design system neutral palette)
- AC-4.2: Primary body text in dark mode is light-coloured and achieves a minimum WCAG AA contrast ratio of 4.5:1 against the dark background
- AC-4.3: Secondary/metadata text in dark mode achieves a minimum WCAG AA contrast ratio of 4.5:1 against the dark background
- AC-4.4: Border and divider colours are visible but not dominant in dark mode
- AC-4.5: The brand colour (`#7A1C1C`) is adjusted in dark mode if necessary to maintain WCAG AA contrast against the dark background
- AC-4.6: No colour inversion is applied to images, videos, or externally embedded content

### AC-5: Site-Wide Coverage

- AC-5.1: All existing pages (homepage, blog listing, individual blog posts, speaking, videos, contact) display correctly in dark mode
- AC-5.2: No component retains hardcoded light-only colour values that are not overridden in dark mode
- AC-5.3: Code blocks in blog posts are appropriately styled in dark mode (readable and visually coherent)
- AC-5.4: Tags, dates, and metadata text are appropriately styled in dark mode
- AC-5.5: The site header and footer are correctly styled in dark mode

### AC-6: Technical Implementation

- AC-6.1: Tailwind CSS `darkMode` is set to `'class'` in `tailwind.config`
- AC-6.2: Dark mode styles use Tailwind's `dark:` variant classes throughout — no inline styles or non-Tailwind CSS overrides for dark mode
- AC-6.3: The theme toggle is implemented as a client component; no server components are converted to client components solely for this feature
- AC-6.4: The synchronous theme application before paint is implemented via an inline `<script>` in the document `<head>` or an equivalent Next.js App Router pattern
- AC-6.5: TypeScript strict mode is observed; no use of `any`

### AC-7: Design System Update

- AC-7.1: `harness/design-system/design-system.md` is updated to include the dark mode colour palette with hex values for background, surface, primary text, secondary text, and border colours
- AC-7.2: The updated design system document notes which brand/accent colours are used as-is versus adjusted for dark mode

### AC-8: Testing

- AC-8.1: A unit test verifies the theme toggle logic: toggling from light sets `dark` class and stores the preference; toggling from dark removes it and stores the updated preference
- AC-8.2: A unit test verifies that `localStorage` reads and writes work correctly for the theme key
- AC-8.3: An integration test verifies that the `ThemeToggle` component renders with the correct `aria-label` in both modes and responds to activation
- AC-8.4: All existing tests continue to pass after the dark mode changes are applied

## Dependencies

- **Existing header component**: The toggle must be placed in the current header; the tech lead must inspect the existing header structure before planning integration
- **Tailwind CSS**: Already present in the project; `darkMode` configuration may need updating from `'media'` to `'class'`
- **Next.js App Router layout**: The inline FOUC-prevention script must be injected via the root layout (`src/app/layout.tsx`) — the implementation plan must address the correct Next.js App Router approach
- **Existing design system**: The light mode palette defined in `harness/design-system/design-system.md` is the basis for deriving the dark mode palette (handled in the Design stage)

---

## Risks

- **FOUC in Next.js App Router**: Server-side rendering and streaming in the App Router make synchronous `<head>` script injection non-trivial. The implementation plan must address this explicitly — a common approach is a `suppressHydrationWarning` pattern on `<html>` combined with an inline script in the root layout
- **Tailwind `darkMode` config change**: If the project currently uses `darkMode: 'media'`, changing to `darkMode: 'class'` may affect any existing dark-variant styles. The implementation plan should audit this before switching
- **Component hardcoding audit**: Some existing components may use hardcoded light colours (Tailwind utilities without `dark:` variants). The scope of changes may be broader than a single component; the build agent must audit all pages and components
- **Client component toggle in server layout**: The header may be a server component. The toggle must be a client component island nested within it — this boundary must be handled correctly to avoid hydration errors
- **`localStorage` not available during SSR**: Theme preference reads must be guarded against server-side execution to avoid runtime errors
