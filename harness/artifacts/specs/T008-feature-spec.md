## Title

Speaking Engagements Page

---

## Feature Goal

Provide a dedicated speaking engagements page that presents upcoming and past speaking appearances from structured markdown content, so visitors can quickly understand where the author is speaking now and where they have spoken previously.

---

## User Value

Visitors need a clear, credible, and easy-to-scan record of the author's public speaking activity. This page gives prospective event organizers, attendees, and general readers a single place to find upcoming appearances, browse speaking history by year, and access supporting talk materials such as slides and recordings when available.

---

## In Scope

- A new page available at `/speaking`.
- Build-time loading of speaking engagement content from `src/data/speaking/YEAR/*.md`.
- Front matter only content files for engagements, with no markdown body content.
- A unified engagement dataset derived from all year directories under `src/data/speaking/`.
- Separation of engagements into `Upcoming` and `Past` based on each engagement's `start` date relative to the current date at build or render time.
- An `Upcoming` section that lists future engagements in ascending start-date order.
- A `Past` section that groups past engagements by start year in descending year order.
- Collapsible year groups for past engagements, collapsed by default on initial page load.
- Display of engagement details: event name, session name, location, start date, optional end date, optional slides link, and optional recording link.
- Empty states for missing upcoming or past engagements.
- Stable ordering for engagements that share the same start date.
- Accessibility requirements for collapsible controls, link semantics, and keyboard interaction.
- Specification of the expected data schema, example content files, and authoring instructions for adding new engagements.

---

## Out of Scope

This feature does not include:

- Search, filtering, or sorting controls beyond the specified default presentation.
- Featured, pinned, or prioritized past engagements.
- External calendar integrations such as RSS, iCal, or speaker directory sync.
- User interactions beyond viewing and following provided links.
- Editorial body content within speaking markdown files.
- Any governance-file updates or workflow progression changes.
- Design-system expansion beyond aligning this page to existing site patterns.


7. The specification includes at least three example engagement files covering:
   - one upcoming engagement with optional links,
   - one past single-day engagement without optional links,
   - one past multi-day engagement with an `end` date.
8. The specification instructs content authors to place each engagement in the year directory that matches the engagement `start` date year and to use a stable descriptive filename.
9. The `Upcoming` section is defined to include all engagements whose `start` date is in the future relative to the current date at build or render time.
10. Upcoming engagements are defined to sort by `start` ascending, so the nearest upcoming event appears first.
11. The `Past` section is defined to include all engagements whose `start` date is in the past relative to the current date at build or render time.
12. Past engagements are grouped by the year derived from `start`, and year groups are ordered descending so the most recent year appears first.
13. All past year groups are collapsed by default on initial page load.
14. Within each past year group, engagements are ordered by `start` descending so the latest engagement in that year appears first.
15. When multiple engagements share the same `start` date, the specification requires deterministic stable ordering by filename or preserved source-list order.
16. Each rendered engagement is defined to display `name`, `sessionName`, `location`, `start`, optional `end`, and optional `slides` and `recording` links when those values exist.
17. If no upcoming engagements exist, the page is required to show a clear empty state in the `Upcoming` section rather than omitting the section entirely.
18. If no past engagements exist, the page is required to show a clear empty state in the `Past` section rather than omitting the section entirely.
19. Year-group toggles are required to be keyboard operable using standard button interaction patterns, including activation by Enter and Space.
20. Collapsible year controls are required to expose expanded and collapsed state through `aria-expanded`, and the revealed content is required to use an appropriate associated grouping or region semantic.
21. Optional slides and recording links are required to be semantically rendered as accessible links with descriptive labels.
22. The page is required to be readable and usable across mobile and desktop viewports while remaining aligned with the existing site design system for spacing, typography, color, and borders.
23. The specification defines `end` dates earlier than `start` as invalid input that must be treated as a content error in downstream implementation.
24. The specification remains implementation-neutral: it defines required behavior and content contracts without mandating component internals or exact visual layout composition.

### Data Schema and Authoring Guidance

Expected front matter contract:

```yaml
name: React Summit
sessionName: Building Next.js Apps at Scale
location: Amsterdam, Netherlands
start: 2026-06-18
end: 2026-06-19
slides: https://example.com/slides
recording: https://example.com/video
```

Example upcoming engagement file:

Path: `src/data/speaking/2026/react-summit-amsterdam.md`

```md
---
name: React Summit
sessionName: Building Next.js Apps at Scale
location: Amsterdam, Netherlands
start: 2026-06-18
end: 2026-06-19
slides: https://speakerdeck.com/example/building-nextjs-apps-at-scale
recording: https://www.youtube.com/watch?v=example1
---
```

Example past multi-day engagement file:

```md
---

location: Amsterdam, Netherlands
start: 2024-11-07
end: 2024-11-08
recording: https://www.youtube.com/watch?v=example2
---
```

Instructions for adding new engagements:

1. Create a markdown file in `src/data/speaking/YYYY/`, where `YYYY` matches the `start` date year.
2. Use front matter only; do not add markdown body content.
3. Use a stable, descriptive filename, for example `event-name-city.md` or `conference-session-topic.md`.
4. Provide all required fields and ensure dates use `YYYY-MM-DD` format.
5. Include `end` only when the engagement spans multiple days.
6. Include `slides` and `recording` only when a public URL is available.
7. Treat any record with `end < start` as invalid and correct the content before publishing.
