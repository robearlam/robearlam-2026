## Technical Approach

The feature is implemented as an additive, fully server-rendered enhancement to the existing blog listing and tag listing pages. No changes are required to the blog post detail page or any other site section.

**Data layer** — The existing `src/lib/blog/posts.ts` data layer contains pure utility functions (`filterPostsByTag`, `paginatePosts`) and async entry points (`getPaginatedBlogPosts`, `getAllBlogPosts`). The strategy is to extend this layer minimally:

1. Add a `filterPostsByYearMonth` pure utility function alongside `filterPostsByTag`, mirroring its signature. This consolidates all filtering logic in one place.
2. Extend `BlogQueryParams` in `src/lib/blog/types.ts` with optional `year` and `month` string fields.
3. Extend `getPaginatedBlogPosts` to invoke the new filter when `year` and `month` are provided, using the same downstream `paginatePosts` call — no duplication of pagination logic.
4. Add a `getTopTags(n: number)` function that derives tag frequency from all posts and returns the top N tag strings sorted by post count descending.
5. Add a `getMonthlyArchive()` function that groups all posts by year+month, counts them, builds human-readable labels (e.g. "March 2026"), and returns the full sorted list (newest first) as typed `MonthlyArchiveEntry` objects. This single function is the sole source of per-month counts; it is called once per page render at the server level and passed as props to the sidebar component.

Per-month post counts are derived entirely inside `getMonthlyArchive()` from the same `getAllBlogPosts()` call used everywhere else. No separate query or second data pass is needed. The count is a simple `Array.length` of the grouped bucket.

**New type** — `MonthlyArchiveEntry` (in `src/lib/blog/types.ts`) carrying `{ year: string; month: string; label: string; count: number }`.

**Components** — Three new server components are introduced in `src/components/blog/`:

- `BlogSidebar` — the shared sidebar container. Accepts an optional `activeTag` prop. Fetches sidebar data (top tags + monthly archive) internally as an async server component, then composes `TopTagsPanel` and `MonthlyArchivePanel`. This isolates all sidebar data-fetching from page-level code.
- `TopTagsPanel` — a pure presentational server component accepting a `tags: string[]` prop and an optional `activeTag: string` prop. Renders the panel with tag links; applies the active highlight via `aria-current="page"` and the brand primary colour class.
- `MonthlyArchivePanel` — a pure presentational server component accepting an `entries: MonthlyArchiveEntry[]` prop. Renders each entry as a link with the month/year label and the count suffix rendered in the secondary text colour.

**Layout** — A thin two-column grid wrapper div (`grid md:grid-cols-[1fr_280px] gap-8`) is introduced inline at the page level in each of the three affected pages. The sidebar is wrapped in a semantic `<aside>` element with `aria-label="Blog navigation"` and hidden below the `md` breakpoint via `hidden md:block`.

**Archive route** — A new Next.js App Router page at `src/app/blog/[year]/[month]/page.tsx`. It uses `generateStaticParams` (backed by a new `getAllArchiveMonths()` data function) to statically generate all valid year/month combinations at build time, consistent with how the tag route handles `generateStaticParams`. The page follows the same structure as the tag listing page: a heading showing the human-readable month/year, the same `BlogFeedClient` component for incremental loading, and the shared `BlogSidebar`.

## Risks

1. **Blog post date parsing** — The `publishDate` field in frontmatter is validated as a parseable date string but no canonical format is enforced. Month/year grouping logic must use `Date.parse` or `new Date()` consistently with the existing `sortPostsByDateDesc` utility to avoid off-by-one month issues with timezone offsets. This should be validated early in Slice 1/2.

2. **Route segment collision** — The new dynamic route `src/app/blog/[year]/[month]/page.tsx` adds two dynamic segments below `/blog`. The existing `src/app/blog/[slug]` single-segment route does not conflict because Next.js matches routes by segment count. These routes should coexist cleanly but should be verified during Slice 6.

3. **Sidebar data coupling** — If `BlogSidebar` fetches its own data internally (the recommended approach), it introduces an additional `getAllBlogPosts()` call per page render beyond those already made by the page component. In a statically generated context this is not a production runtime cost, but it should be confirmed that Next.js deduplicates async calls within a single render pass or that the impact is acceptable for a static site.

4. **Tag listing page layout coupling** — The current tag listing page uses a flat `<section>` wrapper. Introducing the two-column grid wrapper around it should be non-breaking, but if padding, max-width, or other layout styles are applied at the section level, they may need adjustment.

5. **Empty archive month static generation** — `generateStaticParams` generates paths for months with at least one post. A valid-but-empty archive URL cannot be reached from a statically generated build unless the data changes at runtime. The empty-state requirement is retained for correctness but this case may only be exercisable via a fixture.

## Assumptions

1. Blog post `publishDate` values are consistently parseable ISO date strings across all markdown files in `data/blogs/`. Month/year derivation will treat all dates as UTC to avoid timezone-induced month boundary issues.

2. The existing `BlogFeedClient` component will need a small extension to accept `year` and `month` props for archive route progressive loading, analogous to the existing `tag` prop. This is within scope.

3. The two-column layout wrapper is implemented as an inline Tailwind-classed div within each page rather than as a shared layout component, consistent with the existing codebase pattern.

4. shadcn/ui components are not required for the sidebar panels — the existing design system card/border Tailwind pattern is sufficient and consistent with the site editorial style.

5. No internationalization is required. Standard JS Date locale string formatting is acceptable for generating human-readable month labels.

6. The `src/app/blog/[slug]` route does not conflict with the new `src/app/blog/[year]/[month]` two-segment route, as Next.js routes are matched by segment count.
