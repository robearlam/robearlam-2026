## Technical Approach

The implementation mirrors the blog infinite scroll pattern already present in the codebase. The overall strategy is to introduce a server-side paginated data function, a new API route, and a client component that manages scroll-triggered loading, then wire the `/videos` page server component to use the new pattern for its initial render.

**Data layer.** A `getPaginatedVideos()` function is added to `src/lib/videos/videos.ts`. It calls the existing `getAllVideos()` internally, strips the first (featured) video from the sorted list, then applies `offset`-based slicing to the remaining non-featured entries. It returns a typed result object containing the paginated video slice, the total non-featured count, and a `hasMore` boolean — matching the shape of `getPaginatedBlogPosts()`.

**API layer.** A new Next.js App Router API route is created at `src/app/api/videos/route.ts`. The route accepts `limit` and `offset` query parameters, validates them (rejecting invalid values with a 400), and delegates to `getPaginatedVideos()`. Its JSON response shape is compatible with what the client component expects. This route mirrors `src/app/api/blog/route.ts` in structure and validation logic.

**Client component.** A new `VideosGridClient` component is created at `src/components/videos/videos-grid-client.tsx` with the `"use client"` directive. It receives `initialVideos` and `initialHasMore` as props from the server component. It manages local state for the accumulated videos list, current offset, `hasMore`, `isLoading`, and `loadError`. It uses the same `IntersectionObserver`-based sentinel pattern as `BlogFeedClient`, with the same `rootMargin`, in-flight guard, and end-of-list observer disconnect. The loading indicator and end-of-list message inherit the blog pattern's text and markup directly. The grid it renders reuses the existing `VideoCard` component and the same Tailwind grid classes currently used in `VideosGrid`.

**Page and composition layer.** The `/videos` page server component (`src/app/videos/page.tsx`) is updated to call `getPaginatedVideos()` directly (server-side, no HTTP fetch) with `limit=6` and `offset=0` for the first batch, rather than `getAllVideos()`. It continues to retrieve the featured video separately (the first in the full sorted list) and passes the initial paginated batch and `initialHasMore` to `VideosGridClient`. The existing `VideosPageContent` component is updated to accept the server-fetched initial data and render `VideosGridClient` in place of the static `VideosGrid`.

No changes are required to the `VideoCard`, `VideosEmptyState`, `VideoFrontmatter`, or `VideoEntry` types. No existing blog components or utilities are modified.

   Cover: valid request returns correct shape; `offset` pagination steps through the list correctly; featured video is never present in results; invalid parameters return 400.

5. **Create `src/components/videos/videos-grid-client.tsx`.**
   Implement `VideosGridClient` using `"use client"`. Props: `initialVideos: VideoEntry[]`, `initialHasMore: boolean`. Internal state: `videos`, `offset`, `hasMore`, `isLoading`, `loadError`.    Change its props to accept `initialVideos: VideoEntry[]`, `initialHasMore: boolean`, and `featuredVideo: VideoEntry | undefined`.    Replace the `getAllVideos()` call with a server-side call to `getPaginatedVideos({ limit: 6, offset: 0 })`. Separately retrieve the featured video (the first in the date-descending sorted list). Pass `featuredVideo`, `initialVideos`, and `initialHasMore` down to `VideosPageContent`.

## Risks

- **Blog pattern coupling.** `BlogFeedClient` does not expose its intersection observer logic as a shared hook. `VideosGridClient` must replicate the pattern rather than import from the blog component. If the blog pattern is later refactored, the two components must be kept in sync manually. This is an acceptable trade-off given the spec explicitly allows parallel implementations.
- **Small video data set in development.** The current data source may have 7 or fewer videos total, meaning infinite scroll pagination may not be exercisable during manual testing without adding additional test data entries. This is noted in the spec as a known risk.
- **`getAllVideos()` called twice at the page level.** The page server component may end up calling `getAllVideos()` once via `getPaginatedVideos()` and potentially again to retrieve the featured video, resulting in two file-system scans. This can be avoided by calling `getAllVideos()` once, taking the first item as featured, and computing the initial paginated batch in-process. The implementation should consolidate this into a single I/O call.
- **`IntersectionObserver` in test environments.** The integration test environment (jsdom/vitest) does not support `IntersectionObserver` natively. Tests should mock `IntersectionObserver` in the test setup, consistent with any existing patterns in the project.
