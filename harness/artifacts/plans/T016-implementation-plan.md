## Technical Approach

This is a manifest-and-lockfile change, not a feature. The simplest sound approach is:

1. **Fix the reference set first.** Re-fetch the 2026-10-19 Dependabot alert set and turn it into a working table: one row per open advisory, with package, vulnerable range, first patched version, and the version currently resolved in `src/pnpm-lock.yaml`. Every later decision is made against that table, not against memory or this plan's estimates.
2. **Direct bumps before overrides.** Raise direct dependencies and devDependencies in `src/package.json` within their current major so their own dependency trees pick up the patched versions. Then regenerate `src/pnpm-lock.yaml` with pnpm and re-check the table. Use `pnpm.overrides` only for advisories still open after that because the upstream parent has not adopted the fix.
3. **Reuse the existing override block.** `src/package.json` already has a `pnpm.overrides` block from an earlier remediation (PR #38). It already covers `vite`, `fast-uri`, `brace-expansion`, `postcss`, `ip-address`, `hono`, and `@hono/node-server`. Where one of those packages still has an open alert, raise the floor of the existing entry rather than adding a second one. Do not remove existing overrides in this task unless one actively blocks a fix. Pruning stale overrides is a separate hygiene item and can be noted as a follow-up.
4. **The lockfile is regenerated by pnpm, never hand-edited.** `src/pnpm-lock.yaml` is lockfileVersion 9.0 and holds integrity hashes, so editing it by hand cannot produce a sound or verifiable result. CI uses pnpm 10 (`pnpm/action-setup@v4`, `version: 10`) and installs from this lockfile. Build must use pnpm 10.x so the lockfile format matches CI.
5. **Code changes only when forced.** Application code under `src/` changes only if an upgrade breaks lint, typecheck, tests, or the build, or causes a behaviour regression. Each change is recorded with its reason (spec AC8). `src/data/` is never touched (AC7).
6. **Evidence over narration.** Resolution is proven from `src/pnpm-lock.yaml`. Runtime behaviour is proven from command output or a cited CI run. Anything not run is recorded as unverified (spec AC12, AC13).

### pnpm availability (carry-forward)

pnpm was not found locally at run start. Build handles it in this order:

1. **Check** whether `pnpm` is on PATH.
2. **If it is missing, Build may provision pnpm 10 without changing the repository.** First choice is Corepack (bundled with Node), activating a pnpm 10.x release. Fallback is a one-off invocation through `npx` pinned to pnpm 10. Build must not add a `packageManager` field or any other repository change just to provision tooling. Build records in its summary which method worked and the exact pnpm version.
3. **If neither works** (no network, permission denied, Corepack unavailable), Build **cannot regenerate the lockfile soundly** and must stop and escalate to the orchestrator as blocked. It must not edit `src/pnpm-lock.yaml` by hand, must not fall back to `npm install` (that would produce or modify an npm `package-lock.json`), and must not report any validation command as passed. If pnpm is missing, spec AC13 allows runtime validation to be recorded as unverified, but it does not cover lockfile regeneration, which needs pnpm.
4. **If pnpm works for install but a validation command cannot run** (for example, Playwright browsers cannot be installed locally), record that command as unverified with the reason, and rely on the CI workflow run (AC13b) for build and e2e evidence.

## Implementation Steps

1. **Baseline (Slice 1).** Provision pnpm 10 as described under pnpm availability. If that fails, stop and escalate. Fetch the alert list and build the advisory table. Run a frozen-lockfile install on the untouched tree and record the result.
2. **Next.js (Slice 2).** Move `next` and `eslint-config-next` to the same 16.3.x release at or above 16.3.8. Regenerate the lockfile. Run lint, typecheck, and build. Fix only what the upgrade breaks. Update the advisory table.
3. **Direct bumps (Slice 3).** Bump `mermaid`, `vitest`, and the parents identified with `pnpm why`, within their current majors. Raise the `vite` override floor. Regenerate the lockfile, run the unit and integration tests, and update the table.
4. **Overrides (Slice 4).** For each advisory still open, decide: no patch exists (go to dispositions), patch is compatible (add or raise an override), or patch is incompatible with the parent (go to dispositions with reason). Regenerate the lockfile after the overrides. Record each override in the register.
5. **Consistency check.** Run a frozen-lockfile install to confirm the manifest and lockfile agree (AC3). Confirm `next` has a single resolved version (AC1). List each in-scope package's resolved version against its fix target (AC2, AC13a).
6. **Full validation (Slice 5).** Run lint, typecheck, test, build, and test:e2e from the repo root with `--dir src`. Record each result honestly. Push the branch so the CI workflow runs, and cite the run if local e2e was not possible.
7. **Dispositions (Slice 6).** Write the disposition list and the final override register into Build's summary for QA.
8. **Staging hygiene.** Stage only `src/package.json`, `src/pnpm-lock.yaml`, and any upgrade-forced source or test changes. Confirm nothing under `src/data/` and neither npm lockfile is staged.

## Risks

- **pnpm cannot be provisioned.** The lockfile cannot be regenerated, so Build is blocked and escalates. There is no partial or hand-edited fallback.
- **Next 16.2 to 16.3 behaviour changes** in caching, metadata image routes, `next/og`, or image optimisation defaults. Mitigated by the build, e2e coverage of the affected routes, and manual route checks.
- **`sharp` 0.34 to 0.35** may be outside what the chosen `next` declares. Forcing it with an override could break image optimisation at runtime without failing the build. Only override if `next` accepts it, or if e2e exercises an optimised image successfully. Otherwise record a disposition.
- **Overrides beyond the parent's declared range** (for example `js-yaml` 3.x, `hono` under the MCP SDK). Prefer scoped selectors, and rely on the test and e2e coverage of the affected surface.
- **Mermaid or DOMPurify output changes** may alter rendered SVG or sanitisation and break diagram tests. Accept only output-equivalent test adjustments, and justify each one.
- **Some fixes are only available in a new major.** AC6 forbids major bumps unless they are the only way to clear an alert. Build records the reason, or chooses a disposition instead.
- **Moving target.** New alerts after 2026-10-19 are follow-ups only.
- **Accidental staging** of `src/data/speaking/2026/symposium-2026.md` or the npm lockfiles. Mitigated by the staging check in step 8.
