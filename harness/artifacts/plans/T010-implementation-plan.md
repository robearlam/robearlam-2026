## Technical Approach

The homepage is implemented as a single Next.js App Router server component (`src/app/page.tsx`). No client components are introduced on this page. All content is sourced at build time via the existing data-layer modules in `src/lib/blog/`, `src/lib/videos/`, and `src/lib/speaking/`.

The existing placeholder content in `src/app/page.tsx` (the generic `HeroSection`, static `ContentBlock`/`SectionWrapper` passages) is replaced entirely with the new homepage structure.

### Component Strategy

All homepage-specific presentational components are placed in a new `src/components/homepage/` directory:

- **`HomepageHero`** — A new component accepting author name, intro text, and image src/alt/dimensions. It composes the responsive two-column (desktop) / stacked (mobile) hero layout and renders the profile photo using Next.js `<Image>` with `priority` enabled. This component does **not** modify or extend the existing `HeroSection` editorial component; it is entirely independent, preventing any regression to other pages that use `HeroSection`.
- **`HomepageSection`** — A lightweight wrapper that provides a consistent `<h2>` heading, content area, and optional CTA link for each content section. Used to wrap the blogs, videos, and speaking regions, ensuring visual and structural consistency across sections.

### Reuse Strategy

- **`BlogPostCard`** (`src/components/blog/blog-post-card.tsx`) — reused directly in the blogs section. If its prop interface does not cover all required homepage display fields (title, publishDate, abstract), minimal prop-compatible usage or a thin wrapper prop selection is applied without altering the shared component.
- **`VideoCard`** (`src/components/videos/video-card.tsx`) — reused directly in the videos section. Same adaptation rule applies.
- **`SiteShell`** — the global layout wrapper is already applied via the root layout; no change required.

### Data Fetching

- Blogs: call the existing blog data-layer access point, sort by `publishDate` descending, take the first 3 entries. Slicing and sorting logic lives in `src/app/page.tsx` or a thin helper in `src/lib/blog/` if a suitable function does not already exist.
- Videos: call the existing videos data-layer access point, take the 3 most recently added entries.
- Speaking: call the existing speaking data-layer access point, filter to entries whose `start` date is on or after the current build date (evaluated at build time using `new Date()` within the server component). If at least one upcoming event is found, the speaking section is rendered; otherwise the section is entirely omitted from the component tree.

### Styling

All layout and visual decisions use Tailwind utility classes only. The design-system conventions from the design note (max-w-4xl container, generous vertical padding, responsive grid breakpoints, Inter typography) are applied through standard Tailwind tokens. No inline styles are introduced.

## Risks

1. **`BlogPostCard` prop incompatibility** — The existing `BlogPostCard` component may not expose an `abstract` or `publishDate` prop at the expected shape. Inspect the component signature before assuming direct reuse; a thin display-only wrapper may be needed.

2. **`VideoCard` thumbnail rendering** — If `VideoCard` does not already use Next.js `<Image>` internally, thumbnails may render as raw `<img>` tags. This is acceptable for the homepage slice but should be noted for future refinement; do not alter the shared `VideoCard` component as part of this task.

3. **Date timezone sensitivity in speaking filter** — `new Date()` evaluated in the server component at build time uses the server's local timezone. If speaking `start` dates are stored as date-only strings (e.g. `"2026-04-10"`), parsing them naively with `new Date(dateString)` may produce off-by-one results depending on timezone offset. The data-layer helper should normalise the comparison (e.g. compare date portions only, not full timestamps).

4. **Fewer than 3 blog/video entries** — If the live data contains fewer than 3 posts or videos, the homepage will render fewer cards. The spec's open question on this was not formally resolved; the safest baseline is to render however many entries are available (no minimum enforcement, no section hiding). If the product owner requires a different behaviour, this must be resolved before build starts.

5. **`HomepageHero` image dimensions** — The `<Image>` component requires explicit `width` and `height`. The actual pixel dimensions of `/img/rob.png` must be confirmed before setting these attributes to avoid distorted rendering.
