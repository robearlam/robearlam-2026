## Title

Dark Mode Support

---

## Feature Overview

The site currently renders only in a light colour scheme. This feature adds a global dark mode that respects the user's OS colour scheme preference by default and allows manual override via a toggle in the site header. The chosen preference is persisted so return visitors see their preferred mode immediately without a flash of the wrong theme.

---

## Design Intent

The design must extend the existing visual system into a dark mode without introducing a separate design language. The guiding principles from the design system — content-first, typographically-led, calm and restrained — apply equally in dark mode.

Specific intent:

- **Dark but not stark**: The dark background should be a deep neutral grey, not pure black. This reduces harsh contrast and keeps the reading experience comfortable.
- **Brand continuity**: The dark red brand colour must remain recognisable in dark mode. The existing `#7A1C1C` is too dark for legibility on dark backgrounds and will be lightened to a mid-bright red that preserves the brand character.
- **Typography-led**: Text contrast is the primary concern. Primary text should be near-white but not pure white; secondary text should be clearly subordinate but still legible.
- **Visual restraint in both modes**: The dark mode palette should feel as restrained as the light mode — no dramatic neons or saturated tones. The accent amber can remain unchanged.
- **Invisible switching**: The toggle must switch modes instantly and without visual disruption. FOUC prevention is a first-class design concern.

## Page / Feature Structure

Dark mode is a global, site-wide concern, not a per-page layout. The structure has two main parts:

**1. Theme Initialisation Layer (invisible, pre-render)**
An inline script executes synchronously in the document `<head>` before any content renders. It reads `localStorage` and `prefers-color-scheme`, then applies or withholds the `dark` CSS class on the `<html>` element. This layer has no visible UI.

**2. Theme Toggle (visible, interactive)**
A single toggle button placed in the site header. It is the user's only control point for switching between light and dark mode. It must be accessible from every page at every breakpoint.

---

## Section Breakdown

### Theme Initialisation Script

**Purpose:** Apply the user's preferred theme before page paint to prevent FOUC.

**Behaviour:**
- Reads `localStorage` for a stored theme key (e.g. `theme`)
- If value is `'dark'`, applies `dark` class to `<html>`
- If value is `'light'`, ensures `dark` class is absent
- If no value, reads `window.matchMedia('(prefers-color-scheme: dark)')` and applies class accordingly

**Visual guidance:** This component has no visual output. Its only effect is the presence or absence of the `dark` class on `<html>`.

---

### Theme Toggle — Header Placement

**Purpose:** Allow users to switch between light and dark mode from any page.

**Placement:** Inline with the existing header navigation items, right-aligned within the header container. On desktop it sits at the trailing edge of the navigation. On mobile it should be consistently accessible — placed either within the mobile menu or as a persistent icon at the trailing edge of the collapsed header bar.

**Visual design:**
- Button appearance: icon-only, no visible label text. The icon communicates the action, not the current state — i.e. the icon shown is the mode you will *switch to*, not the mode you are currently in.
  - When in light mode: show a **moon icon** ("switch to dark")
  - When in dark mode: show a **sun icon** ("switch to light")
- The button should have no border or filled background in its default state — it should read as a subtle interactive icon consistent with the header's minimal style.
- On hover: a subtle colour shift (consistent with the design system's interaction pattern — slight colour change, no heavy shadow or fill).
- Icon size: approximately 20–22px. The clickable area must be padded to meet the 44×44px minimum tap target.
- The button should feel at home in the header alongside nav links — calm and unobtrusive, never calling more attention than the nav items themselves.

**Colour in light mode:** Icon colour matches the existing header text/link colour (approximately `#1F1F1F` or consistent with nav link colour).

**Colour in dark mode:** Icon colour is the dark mode primary text colour (`#F0F0F0`), matching the dark mode nav text treatment.

### Dark Mode Palette

The following palette is derived from the existing light mode design system and must stay aligned with the values documented in `harness/design-system/design-system.md` and implemented in `src/app/globals.css`. In implementation, prefer semantic theme tokens and utility classes such as `bg-background`, `bg-card`, `text-foreground`, and `border-border` rather than hard-coded dark-mode hex utilities.

| Token | Light Mode | Dark Mode |
|---|---|---|
| Background | `#FFFFFF` | `#1F1616` |
| Surface (cards, panels) | `#FFFFFF` | `#2A1E1E` |
| Primary text | `#1F1F1F` | `#FFFFFF` |
| Secondary / metadata text | `#6B6B6B` | `#C9BFBF` |
| Borders / dividers | `#E5E5E5` | `#4A3939` |
| Muted surface | — | `#352727` |
| Brand primary | `#7A1C1C` | `#B23A3A` |
| Brand secondary | `#B23A3A` | `#7A1C1C` |
| Accent | `#D97706` | `#D97706` |

**Palette rationale:**
- Background `#1F1616` is a warm dark red-brown — not pure black. It softens the reading experience and complements the dark red brand.
- Surface `#2A1E1E` provides a subtle elevation distinction for cards and panels without heavy shadow.
- Primary text `#FFFFFF` is white for maximum readability on the warm dark background.
- Secondary text `#C9BFBF` is clearly subordinate to primary text and achieves strong contrast on `#1F1616`.
- Brand primary is lightened from `#7A1C1C` to `#B23A3A` — a mid-bright red that maintains brand identity and legibility on dark backgrounds.
- Accent amber `#D97706` carries across unchanged; it works well in both modes.

**Contrast check (against `#1F1616` background):**
- `#FFFFFF` primary text: ~14:1 — exceeds WCAG AAA
- `#C9BFBF` secondary text: ~8:1 — exceeds WCAG AA
- `#B23A3A` brand primary: ~3.5:1 — meets WCAG AA for large text

---

### Site-Wide Colour Application

All pages and components apply dark mode colours via semantic Tailwind utility classes that resolve to CSS custom properties defined under the `.dark` class selector:

- **Body / page background**: `bg-background`
- **Card / surface backgrounds**: `bg-card`
- **Primary text**: `text-foreground`
- **Secondary / metadata text**: `text-muted-foreground`
- **Borders**: `border-border`
- **Brand accent links and active states**: `text-primary`

Images, video embeds, and external content are not modified. The `dark:` class is not applied to `img` or iframe elements.

Code blocks in blog posts should shift to a dark surface (`dark:bg-[#242424]` or similar) with appropriately adjusted syntax highlight token colours.

## Component Recommendations

**`ThemeToggle` — new client component**
A focused, single-responsibility client component. Responsibilities:
- reads current theme from component state (initialised from `localStorage` or system preference)
- renders the correct icon for the current mode (sun or moon — icon library to be determined by tech lead from existing project tooling)
- on activation, toggles the `dark` class on `document.documentElement`, writes the new preference to `localStorage`, and updates its own icon state
- exposes a correct `aria-label` that reflects the forthcoming action
- is designed to mount cleanly within a server-rendered header without causing hydration errors

**Placement in header:** The toggle is inserted as a child of the existing header component. The header itself remains a server component; `ThemeToggle` is the only `"use client"` island needed.

**Existing components receiving `dark:` variants:** All existing layout and content components (header, footer, nav, blog cards, video cards, speaking items, section wrappers) receive appropriate Tailwind `dark:` class additions. No structural changes to these components are required — the change is additive.

## Responsive Behaviour

### Mobile

- The toggle is accessible without opening any menu if possible — a small icon button at the trailing edge of the collapsed header bar (alongside or near the mobile menu trigger) is the preferred placement.
- If the header collapses to show only a logo and hamburger, the toggle may be placed as the first item inside the mobile menu.
- Tap target must meet 44×44px minimum. This is achieved via padding around the icon, not by enlarging the icon itself.
- The icon should not compete visually with the menu trigger — it should feel equally subtle.

### Tablet

- The toggle appears inline in the header navigation, consistent with desktop behaviour.
- Spacing between the toggle and adjacent nav items should follow the standard spacing scale.

### Desktop

- The toggle sits at the trailing edge of the header navigation row.
- It does not require a visible text label at any breakpoint.
- Hover state is a subtle colour shift consistent with nav link hover behaviour.

### Cross-breakpoint

- The toggle must be present and functional at all breakpoints — it must never be hidden or disabled.
- The `dark` class on `<html>` persists across all breakpoints; there is no breakpoint-conditional theme.

---

## Accessibility Considerations

- The toggle is a `<button>` element, not a `<div>` or `<span>`, to ensure native keyboard and screen reader support.
- `aria-label` is dynamic: "Switch to dark mode" when in light mode, "Switch to light mode" when in dark mode.
- The icon alone communicates the affordance visually; the `aria-label` communicates it for assistive technology.
- Focus ring must be visible in both light and dark modes — using the design system's standard focus treatment (consistent with other interactive elements on the site).
- Contrast ratios defined in the palette section must be met across all text elements in dark mode.
- The theme switch must not move focus or disrupt reading flow when activated.
- Heading hierarchy and semantic structure are not affected by the theme class — the `dark` class on `<html>` only affects colour, not structure.

## Risks

- **FOUC risk in Next.js App Router**: Inline script placement in a streaming SSR context requires care. The standard approach (`suppressHydrationWarning` on `<html>` + inline `<script>` before body content) is well-established but must be tested. The tech lead should verify the correct App Router pattern.
- **Tailwind config change impact**: Switching `darkMode` from `'media'` to `'class'` (if currently `'media'`) removes automatic OS-based dark mode from Tailwind. Any existing `dark:` classes that relied on `media` strategy will now require the `dark` class on `<html>` — this is correct behaviour but must be verified against the existing codebase.
- **Component audit scope**: The build agent must audit all components for hardcoded light-only colours. The extent of this work depends on existing usage patterns and could be broader than anticipated. The design calls for additive `dark:` classes, not structural rewrites.
- **Icon source**: The design calls for sun/moon icons. The tech lead should confirm whether the existing project has an icon system (e.g. Heroicons, Lucide, or inline SVG) before implementation begins, to avoid introducing an unnecessary dependency.
