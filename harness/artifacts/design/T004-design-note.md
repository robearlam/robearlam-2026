## Title

Editorial UI System Refactor from Design Reference

---

## Feature Overview

The production site is refactored so that every page conforms to a single editorial design system. A small layer of reusable editorial components (header, footer, section wrapper, hero, content block) is introduced, the homepage is restructured into clearly defined sections with real content, blog presentation is improved while preserving all data logic, and the contact page is simplified. Typography, spacing, and colour are made consistent across every route.

The result is a cohesive, calm, readable site that feels intentionally designed rather than assembled from defaults.

---

## Design Intent

### Experience objective

Visitors should perceive the site as a single, quietly confident editorial publication. Every page should feel like it belongs to the same visual system, with content as the clear focus.

### Visual and structural priorities

- **Typography-led hierarchy.** Heading scale, body size, and line height do the heavy lifting for visual structure. Decorative elements are avoided.
- **Neutral-dominant palette.** The interface is built on warm neutrals (`#FFFFFF` background, `#FFFFFF` surface, `#1F1F1F` text). Dark red (`#7A1C1C`) appears only as a controlled accent — active nav state, occasional link emphasis — never as a dominant colour.
- **Consistent vertical rhythm.** All sections use the spacing scale defined in the design system. Section gaps range from `space-y-10` to `space-y-16`; intra-section content uses `space-y-4` to `space-y-6`.
- **Narrow, readable content width.** The main container is centred and constrained between `max-w-3xl` and `max-w-4xl`, ensuring comfortable line length on all screens.

### Design system alignment

Every decision — colour choice, font size, spacing value, component shape — must trace back to `harness/design-system/design-system.md`. No ad-hoc values.

### Usability considerations

- Mobile-first layout approach with progressive enhancement for wider viewports.
- Visible focus states on all interactive elements.
- Logical heading order on every page (no skipped levels).
- Sufficient contrast on all text (WCAG AA minimum).

## Page / Feature Structure

The site follows a consistent page skeleton across all routes:

1. **Site header** — fixed at the top of each page; contains site identity and navigation.
2. **Main content area** — centred container (`max-w-3xl` to `max-w-4xl`) holding page-specific content composed from editorial sections.
3. **Site footer** — lightweight, editorial-tone footer at the bottom of each page.

Within the main content area, pages are composed from a predictable progression:

- Optional **hero section** (page-level introduction with a prominent heading and brief lead text).
- One or more **content sections**, each wrapped in a section wrapper that enforces consistent vertical spacing.
- Content sections contain **content blocks** — standard prose containers for body text, lists, or grouped elements.

This hierarchy maps directly to the design system's Page → Section → Container → Content model.

## Section Breakdown

### Site Header

**Purpose:** Persistent site identity and navigation across all pages.

**Expected content:**
- Site name or wordmark (text-based, not a logo image) aligned left.
- Navigation links: Home, Blog, About, Contact.

**Visual guidance:**
- Clean horizontal bar on a white or near-white surface.
- Navigation links use neutral text colour by default. The currently active route uses the dark red accent (`#7A1C1C`) to indicate state.
- Subtle bottom border (`#E5E5E5`) separates the header from page content.
- Typography follows the body text scale (16–18px); navigation should not dominate the page.

**Interaction:**
- On desktop, navigation links are displayed inline/horizontally beside or below the site name.
- On mobile, navigation collapses into a hamburger/toggle button that reveals a vertical list of links. The menu opens and closes on activation. Implementation should be lightweight — CSS-driven with minimal JS state (a single boolean toggle).

---

### Hero Section

**Purpose:** Provide a prominent page-level introduction at the top of a page.

**Expected content:**
- A large heading (H1, 36–48px).
- A brief lead paragraph of supporting text (1–3 sentences).

**Visual guidance:**
- Generous vertical padding above and below (section-level spacing: `space-y-10` to `space-y-16`).
- No background colour or image — the hero relies on typography scale and whitespace for emphasis.
- Lead text uses muted secondary text colour (`#6B6B6B`) to avoid competing with the heading.

**Where used:** Homepage (required), optionally on About and Contact pages.

---

### Section Wrapper

**Purpose:** Enforce consistent vertical spacing between major page sections.

**Expected content:** Wraps any group of content that forms a logical section.

**Visual guidance:**
- Applies section-level vertical spacing (`space-y-10` to `space-y-16`) between siblings.
- No backgrounds, borders, or decoration. Spacing alone creates separation.

**Where used:** Every page, wrapping each distinct content region.

---

### Content Block

**Purpose:** Standard prose container for body copy and grouped content.

**Expected content:** Paragraphs, lists, small groupings of related information.

**Visual guidance:**
- Body text at 16–18px, generous line height.
- Internal spacing of `space-y-4` to `space-y-6`.
- Headings within content blocks follow the H2–H4 hierarchy.
- Text colour is primary (`#1F1F1F`); metadata or secondary text uses `#6B6B6B`.

**Where used:** All pages within section wrappers.

---

### Site Footer

**Purpose:** Close each page with minimal editorial-appropriate content.

**Expected content:**
- A single line of copyright or site attribution text.
- Optionally a small set of navigation links (matching the header links) displayed inline.

**Visual guidance:**
- Visually quieter than the header — smaller/muted text (`#6B6B6B`).
- Separated from content by a subtle top border (`#E5E5E5`) or by section-level spacing alone.
- No social icon grids, no multi-column link blocks.

---

### Homepage

**Structure:**
1. Hero section — introduces the site with a strong H1 and a brief personal or professional statement (real content, not placeholder).
2. One or two content sections — could introduce recent blog posts, a brief professional summary, or areas of interest. Content should be real and representative.

**Visual guidance:**
- Sections flow vertically with section-level spacing.
- No decorative cards, background panels, or colour blocks. Structure comes from type and space.

---

### Blog Listing Page

**Structure:**
1. Page heading (H1) — e.g. "Blog" or "Writing".
2. List of blog post previews.

**Post preview design:**
- Each preview shows the post title (H2 or H3, linked), date (muted secondary text), and an optional short excerpt.
- Previews are separated by spacing or a subtle divider (`#E5E5E5`).
- No heavy card styling — keep the presentation flat and editorial.

**Data logic:** All existing data-fetching, routing, and API behaviour remains untouched. Only presentation changes.

---

### Blog Post Page

**Structure:**
1. Post title (H1).
2. Date and metadata (muted secondary text, below the title).
3. Post body rendered with editorial typography (content block styling).

**Visual guidance:**
- The post body should use the content block prose styling: comfortable body size, generous line height, constrained width.
- Headings within post content follow the H2–H4 hierarchy.

**Data logic:** Existing markdown parsing, routing, and data flow are unchanged.

---

### About Page

**Structure:**
1. Page heading (H1).
2. One or more content blocks with biographical or professional information.

**Visual guidance:**
- Follows the standard section wrapper / content block pattern.
- No special components required beyond what the editorial layer provides.

---

### Contact Page

**Structure:**
1. Page heading (H1).
2. A brief introductory paragraph.
3. Contact information displayed directly (email address, or a simple static form for visual structure only).

**Visual guidance:**
- Clean and minimal. If a form is present, it should not include fake submission behaviour — either it is genuinely functional or it is presented as a static layout element with no misleading submit action.
- Form inputs, if present, should be simple: neutral borders, adequate padding, readable label text.

## Component Recommendations

The following reusable component roles should be introduced:

| Component | Role |
|---|---|
| **Site Header** | Renders site identity and responsive navigation. Used in the shared layout so it appears on every page. |
| **Site Footer** | Renders minimal footer content. Used in the shared layout. |
| **Section Wrapper** | Applies consistent section-level spacing. Wraps major content regions on any page. |
| **Hero Section** | Renders a prominent H1 + lead text block. Used at the top of pages that need a strong introduction. |
| **Content Block** | Standard prose container with editorial typography. Used inside section wrappers for body content. |

**Relationship to existing components:**
- The existing `site-nav.tsx` and `site-shell.tsx` provide current layout structure. These should be refactored or replaced by the new header, footer, and layout arrangement rather than layered on top.
- The shared root `layout.tsx` should compose the header, main content area, and footer into the global page shell.

**No new UI libraries.** The editorial component layer should be built with standard React components and Tailwind utility classes. shadcn/ui primitives already in the project may be retained where they serve a purpose, but no additional component library imports should be introduced.

## Responsive Behaviour

### Mobile

- The site header collapses navigation into a toggle/hamburger button. When activated, links appear in a vertical stack below the header bar.
- Content container uses horizontal padding (`px-4` to `px-6`) to ensure breathing room.
- Typography scales remain comfortable — body text should not drop below 16px.
- Section spacing may be slightly reduced (e.g. `space-y-8` to `space-y-10`) to avoid excessive scrolling on short content pages.
- Blog post previews stack vertically with clear separation.

### Tablet

- Navigation may remain collapsed or expand to horizontal depending on available width. A breakpoint around `md` (768px) is reasonable for the switch.
- Content container width begins to benefit from the max-width constraint (`max-w-3xl` to `max-w-4xl`), centering the content with visible side margins.
- Section spacing returns to the standard scale.

### Desktop

- Navigation is always displayed inline/horizontally.
- Content is centred with comfortable side margins created by the max-width constraint.
- Full section-level spacing (`space-y-10` to `space-y-16`) is used.
- Line length is naturally constrained by the container width, ensuring readability.

### Cross-breakpoint rules

- No horizontal overflow at any viewport width.
- Heading hierarchy and visual weight are preserved across all breakpoints.
- The content container never exceeds `max-w-4xl` regardless of screen size.
- Interactive elements (links, buttons, menu toggle) maintain minimum touch target sizes on mobile.

## Accessibility Considerations

- **Semantic structure:** All pages use semantic HTML landmarks (`<header>`, `<main>`, `<footer>`, `<nav>`, `<section>`).
- **Heading hierarchy:** Every page starts with a single H1. Subsequent headings follow H2 → H3 → H4 without skipping levels.
- **Keyboard accessibility:** The mobile navigation toggle is keyboard-operable. All navigation links and interactive elements are focusable and activatable via keyboard.
- **Visible focus states:** Focus outlines are visible on all interactive elements. Focus styling should use the dark red accent or a clearly visible outline — never removed entirely.
- **Colour contrast:** All text meets WCAG AA contrast ratio minimums against its background. Primary text (`#1F1F1F`) on background (`#FFFFFF`) and surface (`#FFFFFF`) both pass comfortably. Secondary text (`#6B6B6B`) on white must be verified to meet the 4.5:1 ratio for its usage contexts; if it falls short, the shade should be darkened.
- **Meaningful link text:** Navigation links and blog post title links should describe their destination. Avoid "click here" or "read more" without context.
- **Mobile menu accessibility:** The collapsible menu should use appropriate ARIA attributes (`aria-expanded`, `aria-controls`) so screen readers can understand the toggle state.

## Risks

- **Secondary text contrast:** The design system specifies `#6B6B6B` for secondary text. On a `#FFFFFF` surface this yields approximately 5.1:1 contrast (passes AA), but on the `#FFFFFF` background the ratio drops slightly. Implementation should verify and adjust if needed.
- **Mobile menu scope creep:** Implementing a working collapsible menu is the most interactive requirement. There is a risk of over-engineering this with animation, transitions, or complex state. The design intent is a simple boolean toggle with CSS visibility — keep it minimal.
- **Homepage content:** The specification requires "real content" rather than placeholder text. The exact copy for the hero and content sections is not yet defined. This must be resolved before or during implementation planning. Reasonable professional/personal content is acceptable.
- **Refactoring breadth:** The task touches every page and the global layout. The wide surface area increases regression risk. Implementation should proceed incrementally (global shell first, then page-by-page) with test verification at each step.
