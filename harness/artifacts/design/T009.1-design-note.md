## Title

Videos Page — Infinite Scroll Paging

---

## Feature Overview

This feature introduces infinite scroll paging to the `/videos` route, preserving the existing editorial hierarchy while progressively loading additional non-featured video cards in fixed-size batches as the user scrolls toward the end of the list.

On initial render, the page shows the featured video (newest, rendered as a large hero card at the top) followed by exactly 6 non-featured videos (2 rows of 3). As the user scrolls to the bottom of the rendered list, additional batches of 6 non-featured videos are appended automatically until all videos are loaded.

This pattern mirrors the existing blogs page infinite scroll, giving visitors a consistent experience across content sections of the site.

---

## Design Intent

- **Preserve the established editorial hierarchy.** The featured video remains a first-class element at the top of the page, visually distinct from the paged grid. Its presentation must not be altered by the introduction of paging.
- **Maintain visual continuity across load boundaries.** Cards appended via infinite scroll must be indistinguishable from those rendered on initial load — same card component, same spacing, same grid alignment.
- **Minimise perceived loading friction.** Loading state feedback, if present in the blog pattern, should be inherited rather than reinvented. It should be subtle and non-intrusive, consistent with the site's calm, editorial aesthetic.
- **Content-first page experience.** The initial visible content (featured video + first 2 rows of cards) should load quickly and completely, with further content arriving on demand. The page should never feel heavy or blocked.
- **Interaction consistency.** The infinite-scroll trigger and end-of-list experience should be identical to the blogs page. Visitors should not notice any difference in pattern between the two listing pages.

## Page / Feature Structure

The `/videos` page retains its existing structural layout. The introduction of infinite scroll paging does not change the page's top-level hierarchy — it only changes how the non-featured video grid is populated after initial render.

**Structural regions (top to bottom):**

1. **Site navigation** — unchanged global header
2. **Featured video region** — the single hero-scale video card for the newest video; always server-rendered; always positioned above the grid; never part of the paged batch
3. **Non-featured video grid** — responsive 3-column grid of standard video cards; initially populated with 6 server-rendered cards; subsequently extended via infinite scroll
4. **Scroll trigger zone** — a non-visible sentinel element at the bottom of the grid observed by an intersection observer to trigger the next batch load
5. **Loading indicator** — an accessible, unobtrusive indicator rendered while a batch fetch is in progress (inherited from the blog pattern)
6. **End-of-list state** — a visual or accessible signal that all videos have been loaded (inherited from the blog pattern)
7. **Site footer** — unchanged global footer

The page's vertical rhythm follows the standard Section → Container → Content pattern defined by the design system. No additional wrapper or framing regions are introduced.

## Section Breakdown

### Featured Video Region

- **Purpose:** Anchors the editorial hierarchy by highlighting the most recent video as a primary content item. Unchanged from T009.
- **Expected content:** A single large video card for the newest video in date-descending order, displaying title, thumbnail, and relevant metadata.
- **Visual guidance:** Retains the large-format card treatment from T009. No visual changes are required by this feature.
- **Interaction:** Static on load; not part of the infinite-scroll mechanism. The featured video is excluded from all paginated API responses.

### Non-Featured Video Grid

- **Purpose:** Presents the remaining video catalogue in a browseable grid format. This is the region that infinite scroll extends.
- **Expected content:** Standard video cards rendered in a 3-column grid at desktop breakpoints. Initial server render provides 6 cards (2 complete rows); subsequent scroll batches append additional groups of up to 6.
- **Visual guidance:** All cards — whether server-rendered or appended via fetch — must use the same card component and maintain consistent spacing (`gap` within the grid). No visual distinction is introduced between initial and lazily-loaded cards.
- **Interaction:** The grid grows downward as batches are appended. Layout integrity (3-column alignment, consistent card height, gutter spacing) must be preserved across batch boundaries, including the final partial batch.

### Scroll Trigger Zone

- **Purpose:** Houses the intersection observer sentinel that watches for the user approaching the end of the rendered list. Invisible to the user.
- **Expected content:** An empty element positioned immediately below the last rendered card row.
- **Visual guidance:** No visual presence. Should not create any layout shift or gap.
- **Interaction:** When the sentinel enters the viewport (with an appropriate margin), the `loadMore` callback is invoked, triggering a fetch to `/api/videos`. The observer is disconnected once `hasMore` becomes false.

### Loading Indicator

- **Purpose:** Communicates to the user that additional content is being fetched, preventing the impression of a stalled page.
- **Expected content:** Inherited from the blog pattern. Likely a spinner, skeleton row, or minimal text indicator displayed below the current last card row.
- **Visual guidance:** Must follow the site's minimal aesthetic — subtle, neutral tones, no heavy animation. Must not occupy excessive vertical space or cause layout disruption when it appears and disappears.
- **Interaction:** Rendered while a fetch is in-flight. Hidden (or unmounted) once the batch has been appended to the grid.

### End-of-List State

- **Purpose:** Communicates to the user (and assistive technologies) that all available videos are now shown. Prevents repeated or confused fetching.
- **Expected content:** Inherited from the blog pattern. May be a brief message, a visual terminator, or an accessible `aria-live` region signal — whatever the blog pattern uses.
- **Visual guidance:** Should feel like a natural content terminus consistent with the site's typographic design language. No dramatic visual treatment.
- **Interaction:** Once `hasMore` is false and the final batch is appended, this state becomes active. No further intersection observer events should trigger fetch calls.

## Component Recommendations

- **Featured video card** — existing large-format video card component from T009; no changes required.
- **Standard video card** — existing video card component from T009; used unchanged for all non-featured grid items.
- **Video grid layout** — existing responsive grid wrapper from T009; extended to accommodate dynamically appended card batches.
- **`VideosGridClient` client component** — a new `"use client"` component analogous to `BlogFeedClient`. It receives `initialVideos` and `initialHasMore` as props from the server component and manages the scroll-triggered append cycle. It should reuse the intersection observer hook or utility from the blog feature where available.
- **Intersection observer hook / utility** — reused from the blog feature. The same trigger logic, in-flight guard, and debounce behaviour should be inherited rather than re-implemented.
- **Loading indicator** — reused (or directly referenced) from the blog pattern. Must not introduce a visually or behaviourally inconsistent loading state.
- **`/api/videos` route** — a new Next.js API route mirroring `/api/blog`, accepting `limit` and `offset` query parameters, returning paginated non-featured video data and a `hasMore` flag. This is a data boundary, not a UI component, but its response shape must be compatible with what `VideosGridClient` expects.

No new design-system-level component types are required. This feature operates entirely within existing visual and structural patterns.

## Responsive Behaviour

The responsive behaviour of the `/videos` page is unchanged from T009 except that the non-featured grid now grows dynamically. Paged batches must respect the same responsive rules as the initial server-rendered cards.

### Mobile

- The video grid collapses to a single-column layout (1 card per row).
- Infinite scroll trigger still functions — the sentinel element remains positioned below the last card regardless of column count.
- Loading indicator and end-of-list state are rendered within the constrained single-column layout without horizontal overflow.
- Card spacing and typography scale follows the existing mobile treatment.

### Tablet

- The grid transitions to a 2-column layout or remains responsive as defined by T009's existing grid configuration.
- Appended batches follow the same column behaviour as the initial batch.
- No additional spacing or layout adjustment is introduced for appended cards at tablet width.

### Desktop

- The 3-column grid is the canonical desktop layout (matching T009's design intent and the acceptance criteria in the spec).
- Appended batches must align to this 3-column grid without introducing orphaned cards or misaligned last rows until the final (potentially partial) batch.
- A final partial batch (fewer than 6 cards) renders in the 3-column grid with cards left-aligned in the final row; no empty placeholder cells are shown.
- Container width follows the design system guideline (`max-w-3xl` to `max-w-4xl`), consistent with other content pages.

**Cross-breakpoint rules:**

- No horizontal overflow is introduced at any breakpoint.
- Appended cards must not cause layout reflow or cumulative layout shift during the append transition.
- The featured video's visual treatment and position relative to the grid header must remain stable across breakpoints.

## Accessibility Considerations

- **Loading indicator:** Any spinner or loading message rendered during a batch fetch must be announced to screen readers. An `aria-live` region (or equivalent) should declare when new content is loading and when it has been appended. The blog pattern's existing accessible loading state should be preserved exactly.
- **End-of-list state:** If the blog pattern communicates the end of the list via a visible message, that message must be accessible (sufficient contrast, readable font size, logical position in the DOM). If communicated via an `aria-live` region, the region must be present in the DOM from initial render with appropriate `aria-live` and `aria-atomic` attributes.
- **Keyboard focus:** When new cards are appended to the DOM, keyboard focus must not be disrupted. Focus must remain on the element that held it before the append occurred. New cards become naturally focusable in DOM order after append.
- **Scroll trigger sentinel:** The sentinel element must have no accessible role, label, or focus target. It should be invisible and inert to assistive technologies (e.g., `aria-hidden="true"`).
- **Heading hierarchy:** The page heading hierarchy from T009 must be preserved. Video card titles should remain at the appropriate heading level within the card; no heading level changes are introduced by this feature.
- **Colour contrast:** No new colour values are introduced. All text, icons, and interactive states must continue to meet WCAG AA contrast requirements using the design system palette.
- **Semantic structure:** The non-featured grid should remain a meaningful list or group structure semantically. Appended cards must be inserted within the same semantic container, not after it.

## Risks

- **Blog pattern coupling:** If the blog infinite-scroll pattern is tightly coupled (e.g., the intersection observer is embedded directly in the component rather than extracted to a hook), reuse may require light abstraction work. This risk is deferred to implementation planning. The design intent does not change; only the implementation approach may need to accommodate it.
- **Partial batch layout:** A final batch of 1–5 cards rendered in a 3-column grid will produce an incomplete last row. The design relies on left-aligned CSS grid behaviour (no `justify-content: space-between` that would create wide gaps) to handle this gracefully. This must be confirmed during implementation.
- **Cumulative layout shift on append:** If the loading indicator occupies significant vertical space before the batch cards replace it, visible layout jump may occur. The loading indicator design should minimise its vertical footprint or use a reserved-height skeleton to reduce CLS.
- **Small data source:** If the live video dataset contains 6 or fewer non-featured videos, infinite scroll will not activate in practice. QA and manual testing may require supplemental test data to verify scroll behaviour.
