## Title

Auxiliary Site Protocols — RSS Feed, WebFinger, Robots & Sitemap Validation

---

## Feature Overview

This feature adds two new protocol endpoints to the site and validates two existing ones:

1. **RSS feed** at `/rss` — a server-generated RSS 2.0 XML response built from the existing blog data source, allowing feed readers and aggregators to subscribe to blog content.
2. **WebFinger** at `/.well-known/webfinger` — a static JSON response that preserves the Mastodon/ActivityPub identity discovery already published on the live domain.
3. **Robots.txt validation** — confirming the existing implementation remains correct.
4. **Sitemap validation** — confirming the existing implementation remains correct.

None of these endpoints produce user-facing UI. They are machine-readable protocol responses consumed by feed readers, ActivityPub clients, and web crawlers.

---

## Design Intent

- **Zero UI surface** — these are invisible protocol endpoints; no pages, components, or navigation items are introduced.
- **Single source of truth** — all site identity values (`SITE_URL`, `SITE_NAME`, `SITE_DESCRIPTION`) and blog post data (`getAllBlogPosts`) are reused from existing modules; no duplication.
- **Correct content types** — each endpoint returns the precise MIME type expected by its consumers (`application/rss+xml`, `application/jrd+json`).
- **Compatibility preservation** — the WebFinger response replicates the live site payload so Mastodon identity discovery continues to work without interruption.
- **Simplicity** — RSS XML is generated via template literals rather than introducing an XML library dependency, appropriate for a static, well-defined document structure.

## Page / Feature Structure

This feature does not introduce any visible pages or UI components. It adds two Next.js route handlers that return machine-readable responses:

## Section Breakdown

### RSS Feed Endpoint (`/rss`)

**Purpose:** Serve a valid RSS 2.0 feed containing all published blog posts in reverse-chronological order.

**Route:** `src/app/rss/route.ts` — a Next.js Route Handler exporting a named `GET` function.

**Response shape:**

- Content-Type: `application/rss+xml; charset=utf-8`
- Body: well-formed RSS 2.0 XML document

**Channel metadata (sourced from existing constants):**

| Element         | Source                |
| --------------- | --------------------- |
| `<title>`       | `SITE_NAME`           |
| `<link>`        | `SITE_URL`            |
| `<description>` | `SITE_DESCRIPTION`    |
| `<language>`    | `"en"` (static)       |

**Item generation:**

- Call `getAllBlogPosts()` — returns `BlogPostSummary[]` already sorted newest-first.
- For each post, emit an `<item>` containing:
  - `<title>` — `post.title`
  - `<link>` — `canonicalUrl(`/blog/${post.slug}`)` 
  - `<description>` — `post.abstract`
  - `<pubDate>` — `post.publishDate` converted to RFC 822 format (e.g. `new Date(post.publishDate).toUTCString()`)
  - `<guid isPermaLink="true">` — same canonical URL as `<link>`

**XML generation approach — template literals:**

The RSS document is a fixed structure with simple string interpolation. A template-literal approach is the correct choice here because:

- The document shape is static and well-defined (one channel, N items with five fields each).
- No conditional namespaces, attributes, or nesting variations exist.
- Adding a dependency like `fast-xml-parser` or `xmlbuilder2` would be over-engineering for this use case.
- XML special characters in post titles or abstracts must be escaped. A small `escapeXml` helper (replacing `&`, `<`, `>`, `"`, `'`) is sufficient.

**Caching:** The route handler should set `Cache-Control` or use Next.js `revalidate` to avoid regenerating the feed on every request. A static generation approach or reasonable revalidation interval is appropriate.

### WebFinger Endpoint (`/.well-known/webfinger`)

**Purpose:** Return a static JSON Resource Descriptor (JRD) that enables ActivityPub/Mastodon identity discovery for `acct:RobEarlam@mastodon.social` via the `robearlam.com` domain.

**Route:** `src/app/.well-known/webfinger/route.ts` — a Next.js Route Handler exporting a named `GET` function.

**Dot-prefixed directory routing:**

Next.js App Router supports dot-prefixed directory names in the `app/` directory. A folder named `.well-known` is valid and will route to `/.well-known/*` paths. This has been a supported pattern since Next.js 13.4+. No special configuration, rewrites, or middleware are needed.

**Response shape:**

- Content-Type: `application/jrd+json; charset=utf-8`
- Body: static JSON object

**Payload (verbatim from the approved specification):**

```json
{
  "subject": "acct:RobEarlam@mastodon.social",
  "aliases": [
    "https://mastodon.social/@RobEarlam",
    "https://mastodon.social/users/RobEarlam"
  ],
  "links": [
    {
      "rel": "http://webfinger.net/rel/profile-page",
      "type": "text/html",
      "href": "https://mastodon.social/@RobEarlam"
    },
    {
      "rel": "self",
      "type": "application/activity+json",
      "href": "https://mastodon.social/users/RobEarlam"
    },
    {
      "rel": "http://ostatus.org/schema/1.0/subscribe",
      "template": "https://mastodon.social/authorize_interaction?uri={uri}"
    }
  ]
}
```

**Query parameter handling:**

The endpoint must return the identical payload regardless of whether a `resource` query parameter is present. The route handler simply ignores query parameters and always returns the static payload. This matches the live site behavior where both `/.well-known/webfinger` and `/.well-known/webfinger?resource=acct:rob@robearlam.com` return the same response.

This is a deliberate simplification: the site hosts exactly one identity, so there is no need to parse or validate the `resource` parameter.

## Test Strategy

### RSS Feed Tests

- **Content type** — verify the response returns `Content-Type: application/rss+xml; charset=utf-8`.
- **XML structure** — verify the response body contains `<rss version="2.0">`, a `<channel>` element, and the expected channel metadata (`<title>`, `<link>`, `<description>`, `<language>`).
- **Feed items** — verify that items are present when blog posts exist, and that each item contains `<title>`, `<link>`, `<description>`, `<pubDate>`, and `<guid>` elements.
- **Canonical URLs** — verify that item links and guids use the `SITE_URL` constant, not hardcoded domains.
- **XML escaping** — verify that special characters in post titles/abstracts are correctly escaped.

### WebFinger Tests

- **Content type** — verify the response returns `Content-Type: application/jrd+json; charset=utf-8`.
- **Payload shape** — verify the response body matches the expected JSON structure: correct `subject`, `aliases` array, and `links` array with the three expected entries.
- **Query parameter invariance** — verify the response is identical with and without the `?resource=acct:rob@robearlam.com` query parameter.

### Scope

Tests should be unit/integration tests against the route handlers. Since these are Next.js route handlers exporting `GET` functions, tests can invoke the handler directly and assert on the returned `Response` object. Playwright end-to-end tests are not required for machine-readable protocol endpoints but may be added at the implementation team's discretion.

## Risks

- **XML escaping correctness** — blog post titles and abstracts are user-authored content that may contain characters requiring XML escaping (`&`, `<`, `>`, `"`, `'`). The escape helper must handle these correctly to produce valid XML. This is a low-complexity risk but must be covered by tests.
- **`.well-known` build behavior** — while Next.js App Router supports dot-prefixed directories, the implementation should verify during build that the `.well-known` directory is not inadvertently excluded by any tooling (e.g., linting ignore patterns, deployment scripts). This is a low-probability risk.
- **Content-Type header override** — Next.js may attempt to apply default content-type handling. The route handlers must explicitly construct `Response` objects with the correct headers rather than relying on `NextResponse.json()` defaults for the RSS endpoint.
