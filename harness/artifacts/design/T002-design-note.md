## Title

Contact Page v1 (Static)

---

## Feature Overview

This feature introduces a dedicated contact page that sits within the existing global site shell and gives visitors a clear, quick way to find contact details and external profiles. The page is intentionally static and focused on readable presentation rather than interactive workflows.

---

## Design Intent

The page should feel calm, straightforward, and consistent with the existing content-first visual system.

- Prioritize scanability: visitors should identify contact options and profile links within a few seconds.
- Keep structure simple: one clear heading, brief context-setting intro, and grouped contact/link content.
- Align with design-system conventions for typography, spacing rhythm, restrained color usage, and container width.
- Ensure social/profile entries are immediately recognizable through icon + label pairing.
- Preserve usability across breakpoints with no horizontal overflow and comfortable tap targets.

## Page / Feature Structure

The contact page should follow a single-column, content-centered layout inside the shared shell:

1. Page header region: primary page heading and short introductory paragraph.
2. Contact methods region: one or more static direct-contact methods presented as plain content.
3. External profiles region: a list/grid of social/profile links, each with recognizable iconography and clear destination naming.

The structure should maintain semantic heading order and consistent section spacing using the established spacing scale.

---

## Section Breakdown

### Header Region

- Purpose: establish page purpose immediately.
- Expected content: a clear contact-oriented H1 and concise supporting copy.
- Visual guidance: strong typographic hierarchy, restrained color use, generous spacing beneath heading.
- Interaction expectations: none beyond standard text readability.

### Contact Methods Region

- Purpose: provide at least one direct method to reach the owner without requiring form submission.
- Expected content: static method entries (for example, email/contact channel text) in a short, easy-to-scan block.
- Visual guidance: present as grouped content on a surface/background consistent with existing page patterns.
- Interaction expectations: if a method is linkable (such as `mailto:`), it should appear as a standard accessible link; no inputs or submit controls.

### External Profiles Region

- Purpose: expose required social/profile destinations in a recognizable, trustworthy format.
- Expected content: entries for BlueSky, Mastodon, GitHub, LinkedIn, YouTube, and Dev.to.
- Visual guidance: each entry should include icon + text label pairing, consistent spacing, and predictable alignment.
- Interaction expectations: each entry is a standard external link, opening in a new tab with secure external-link attributes.

---

## Component Recommendations

- Use existing page/container and typography patterns established by the shared shell.
- Use existing list/card/link presentation primitives already aligned with the design system.
- Represent social links as reusable profile-link items (icon slot + label + external-link behavior) to ensure consistency.
- Reuse existing icon approach already available in the project stack; do not introduce decorative icon variants that reduce recognizability.
- Reuse standard interactive link states (hover/focus/active) from current design-system behavior.

---

## Responsive Behaviour

### Mobile

- Keep a single-column flow with stacked regions.
- Maintain readable body text sizing and line length.
- Ensure profile links have comfortable tap targets and clear separation.
- Prevent horizontal scrolling in all sections.

### Tablet

- Preserve content-centered layout with increased breathing room.
- Allow profile entries to remain single-column or move to a balanced two-column arrangement if space supports readability.
- Keep heading and intro visually dominant before link content.

### Desktop

- Use wider container spacing while preserving readable content width.
- Profile links may be displayed in multi-column grouping if visual scanning improves and icon/label pairing remains clear.
- Keep section hierarchy explicit through spacing and heading rhythm.

Cross-breakpoint rule: hierarchy and recognizability take priority over dense packing; no breakpoint should compromise readability or link clarity.

---

## Accessibility Considerations

- Use semantic page structure with a single clear H1 and logical section grouping.
- Ensure every social/profile link has a meaningful accessible name that identifies destination.
- Pair icons with visible text labels; icon-only links are not sufficient.
- Preserve visible focus states for keyboard navigation on all interactive links.
- Maintain sufficient text/background contrast per design-system expectations.
- Keep link purpose understandable out of context (no ambiguous “click here” labels).
